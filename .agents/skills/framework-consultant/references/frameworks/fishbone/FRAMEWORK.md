# 特性要因図（フィッシュボーン図 / Ishikawa Diagram）

## 概要

特性要因図は、ある**特性（characteristic＝結果・悪さ）**と、それに影響する**要因（causes/factors）**の
因果関係を、**魚の骨に似た図**で体系的に整理するフレームワーク。別名フィッシュボーン図、石川ダイアグラム、
cause-and-effect diagram。**QC七つ道具**の一つ。

```
                大骨(カテゴリ)        大骨
                   \                  /
         中骨—小骨   \    中骨—小骨   /
   ────────────────────背骨──────────────────▶ 【特性】結果・悪さ
         中骨—小骨   /    中骨—小骨   \
                   /                  \
                大骨                    大骨
```

- **構造**: 右端の魚の頭＝**特性**（分析対象の結果）。左→右の太い矢印＝**背骨**。背骨に刺さる**大骨**＝
  要因の大分類（カテゴリ）。大骨から枝分かれする**中骨・小骨**＝具体的な要因を必要な深さまで展開する。
- **核となる考え方**: 一つの結果に対し、要因を**カテゴリで漏れなく分類**して**発散的に列挙**し、
  深掘りして真因の候補にたどり着くための「思考の地図」。**原因を証明する道具ではなく、候補を構造化して
  考えるための道具**（a thinking tool, not a verdict）。網羅（広さ）に強く、証明（深さ・定量）は別手法で補う。
- **出自（年号は諸説あり・議論がある）**: 考案者は **石川馨（Kaoru Ishikawa, 1915–1989、東京大学教授、
  「日本の品質管理の父」）**。初出年は資料で食い違い、**1943年に川崎製鉄の技術者へ諸要因の関係を説明した
  のが最初**とする英語圏の通説と、**1952〜53年考案**とする日本語資料がある。1960年代に普及し、著書
  『Guide to Quality Control』（日本語原著1968年・英訳はAsian Productivity Organizationから1971年とされる）でQC七つ道具の一つとして記述された。**起源年は断定せず幅で扱う**
  （→出典・要ファクトチェック）。

## いつ使う / 使わない

**使う（適する状況）**
- **不良・クレーム・トラブル・ばらつきの真因究明の「発散段階」**——考えられる要因を、思いつきの羅列でなく
  カテゴリで漏れなく洗い出したいとき。
- **チームで原因を洗い出し、認識を共有**したいとき（QCサークル・改善活動の要因解析ステップ）。
- **一つの結果に複数の要因が絡んでいそう**なとき。どこに手を打つ候補があるかの全体像を1枚で掴む。
- プロセスや現象についての**知識を整理・可視化・教育**したいとき。

**使わない / よくある誤用（アンチパターン）**
- **要因の証明・定量化に使う**——最頻の誤解。特性要因図は**相関の候補を並べるだけで因果を証明しない**。
  検証を省くと「推測の寄せ集め（dumping ground for guesses）」になる。証明は散布図・実験計画・統計へ。
- **カテゴリを埋めて「網羅した気」になる**——4Mの枠が埋まると完全性の錯覚が生まれ、枠外の真因を見落とす。
  カテゴリは補助線であって答えではない。
- **抽象で止める（深掘り不足）**——「教育不足」で止めず「なぜ？」を繰り返して具体・操作可能な要因まで掘る。
- **優先順位をつけず全要因を等価に扱う**——洗い出しの後、影響度・確からしさで絞らないと打ち手に繋がらない。
  定性ツールなので、優先度はパレート図・決定マトリクス等で補う。
- **要因（候補）と原因（検証済み）の混同**——図に並ぶのは**要因候補**。データで裏取りして初めて「原因」。
- **主観・声の大きい人の支配**——思い込みでカテゴリ分けが歪む。事実・データで裏を取り複数視点を入れる。
- **単純な一本道の因果**にはオーバースペック（→なぜなぜ分析単体で足りる）。フィードバックループを含む
  複雑系（要因が相互に絡む）も木構造では表現しきれず不向き。

## 前提と限界

- **前提**: **特性（結果）が1つ・具体的・測定可能**に定義できていること。「品質が悪い」等の漠然テーマは
  発散して破綻する（手順①が要）。要因を出せるだけの**現場知識・データ**、または壁打ちで引き出せる相手が要る。
- **限界（批判を踏まえて）**:
  - **因果を証明しない（相関≠因果）**——構造化の道具であり検証の道具ではない。図で終えると誤診に繋がる。
  - **定性的で優先順位を持たない**——各要因の寄与度・発生確率は図からは分からない。パレート図等で定量補完が要る。
  - **主観・バイアスに弱い**——参加者の経験則に依存し、真の要因が「思いつかない」と図に載らない。
  - **相互作用・時系列を表現できない**——木構造ゆえ、複数要因の掛け合わせやフィードバックループを取り逃す。
  - **完全性の錯覚**——整った図は説得力を持つが、網羅の保証はない。「他にありませんか」を常に問う。
- これらは、**なぜなぜ分析で各枝を真因まで掘る / パレート図・決定マトリクスで要因を優先順位づける /
  最有力候補をデータ・実験で裏取りする**ことで補う（→相性）。図の完成はゴールでなく検証の入口。

## 進め方（手順）

命令形で示す。各ステップの「なぜ」を添える。

1. **特性（結果）を1つ、具体・測定可能に定義して右端に置く。** 「悪さ」で表現する（例:「A工程の外観キズ
   不良率が◯%」）。なぜ: 特性が曖昧だと要因が発散し、羅列で終わる最頻の失敗に直結する。
2. **背骨（左→右の太い矢印）を引く。** なぜ: 全要因を一つの結果に収束させる軸を先に固定する。
3. **大骨＝要因の大分類（カテゴリ）を4〜6本置く。** 定石を目的で選ぶ。
   - **製造の定番 4M**: Man（人）/ Machine（機械・設備）/ Material（材料）/ Method（方法）。
     拡張で +Measurement（測定・検査）=5M、+Environment（環境）=4M1E/6M。
   - **サービス 4S**: Surroundings / Suppliers / Systems / Skills（+Safety）。
   - **マーケ 8P**: Product/Price/Place/Promotion/People/Process/Physical Evidence/Performance。
   なぜ: カテゴリは**抜け漏れ防止の補助線**。対象に合わないカテゴリは足す・差し替える（枠に縛られない）。
   ※工程順に骨を並べる「工程分類型」、先に要因を全部出して後で束ねる「原因列挙型」も選べる（→出典）。
4. **各カテゴリにブレストで要因を出し、中骨・小骨に展開する。** 判断保留で数を出す。
   なぜ: 発散段階では網羅が命。ここで質を問うと候補が痩せる。
5. **各要因を「なぜ？」で深掘りする（なぜなぜ分析を各枝に適用）。** 具体・操作可能な粒度まで掘る。
   なぜ: 抽象な大骨レベルでは打ち手が作れない。真因は小骨の先にある。
6. **有力候補に印を付け、影響度×確からしさで絞る。** 丸で囲む等。上位数個に。
   なぜ: 定性ツールは等価な長大リストを生みがち。絞らないと検証も打ち手も分散する。
7. **チームでレビューし抜け漏れを問う。**「このカテゴリに他は？」「枠外の要因は？」
   なぜ: 完全性の錯覚を崩し、思いつかなかった要因を拾う。
8. **最有力候補をデータ・実験で裏取りする。** 相関を確かめ、対策・再発防止に繋ぐ。
   なぜ: 図の候補は仮説。検証して初めて「原因」になる。ここを省くと誤診する。

## 壁打ち質問リスト

各骨を事実で埋めるために、利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す。

1. 分析したい**特性（結果・悪さ）は具体的に何**ですか？ それは**測定・観測できる形**（不良率・件数・
   発生条件）で言えますか？（曖昧なら「どんな時に、何が、どれくらい」まで具体化する）
2. その現象は**いつ・どこで・どの工程/場面で**起きていますか？ 起きない条件との違いは何ですか？
   （層別のヒント。発生パターンが要因を絞る）
3. 要因のカテゴリ（大骨）は何が適切ですか？ 製造なら**4M（人・機械・材料・方法）**で漏れなさそうですか、
   それとも測定・環境やサービス/マーケ系のカテゴリを足すべきですか？
4. 各カテゴリで、**思い当たる要因を判断せず挙げると**何が出ますか？（人: 教育/手順の理解、機械: 摩耗/設定、
   材料: ロット差/保管、方法: 標準の有無/守られ方 …をひと通り）
5. その要因について「**なぜそうなるのか**」をあと2〜3回掘れますか？（例: ミスが多い→なぜ→手順書が古い→
   なぜ→更新の担当が不明…と真因側へ）
6. 挙がった要因のうち、**最も影響が大きそう／起きている確からしさが高い**のはどれですか？その**根拠（データ・
   目撃・再現性）**はありますか、それともまだ推測ですか？
7. すでに**データで確かめられている要因**と、**まだ仮説の要因**はどれですか？（相関を確認する手立ては？）
8. この分析は**誰の視点**で作っていますか？ 現場・保全・品質など**別の立場なら違う要因**が挙がりませんか？

## 出力フォーマット

ALWAYS この2段構えで出力する（要因の構造化 → 深掘り・検証への橋渡し）。骨の階層はテキストで表す。

```
【特性要因図】特性(結果): <測定可能な悪さ> ／ 発生条件・層別: <いつ・どこで>
  ■ 大骨[人 Man]
     - 中骨: <要因> → 小骨: <なぜ→具体要因>
     - 中骨: <要因> → 小骨: <…>
  ■ 大骨[機械 Machine]
     - 中骨: <要因> → 小骨: <…>
  ■ 大骨[材料 Material]
     - 中骨: <要因> → 小骨: <…>
  ■ 大骨[方法 Method]
     - 中骨: <要因> → 小骨: <…>
  （大骨は例示。対象に応じて差し替える: 製造=4M/5M/6M、サービス=4S、マーケ=8P。測定・環境の追加も可）

【有力候補（要検証）】影響度×確からしさで絞った上位の要因
  ◎ <要因1> — 根拠: <データ/目撃/再現性 or 「推測」> — 確かめ方: <検証手段>
  ◎ <要因2> — 根拠: <…> — 確かめ方: <…>

【次の一手】<検証すべき仮説・取得すべきデータ・当てるべき対策を1〜3個>
【未確認の前提】<事実確認が要る点（壁打ちで埋める）／要因か原因かの区別>
```

## 具体例（ワークスルー）

対象を一般化した例（架空の数値・企業名は用いない）。ある製造ラインで**製品表面のキズ不良が続いている**場面。

- **手順①特性**: 「A工程後の外観検査でキズ不良が発生している」を特性に置く（本来は不良率など測定値を伴う）。
- **手順③大骨（4M）**: 人 / 機械 / 材料 / 方法 の4本を置く（＋必要なら測定・環境）。
- **手順④中骨・小骨（発散）**:
  - 人(Man): 取り扱い時の接触 → 小骨: 手順の理解不足 / 交代要員への教育差。
  - 機械(Machine): 搬送部の摩耗 → 小骨: 定期保全の間隔 / ガイドの調整ずれ。
  - 材料(Material): 素材ロット差 → 小骨: 保管中の擦れ / 入荷検査の基準。
  - 方法(Method): 標準作業の有無 → 小骨: 標準はあるが守られていない / 手順書が現状と不一致。
- **手順⑤深掘り（なぜ）**: 「方法: 標準が守られない」→なぜ→「手順書が古い」→なぜ→「更新の担当・トリガーが
  未定」。真因候補は小骨の先に現れる。
- **手順⑥絞り込み**: 影響が大きく再現性が見えそうな「搬送部の摩耗（機械）」と「手順書の陳腐化（方法）」に印。
- **手順⑧検証への橋渡し**:
  - 有力候補「搬送部の摩耗」→ 確かめ方: 発生ロットと保全記録・摩耗量の相関をデータで確認。
  - 有力候補「手順書の陳腐化」→ 確かめ方: 現行手順と実作業の突き合わせ・作業者ヒアリング。
- **次の一手**: 上記2つを実データで検証し、相関が確認できた要因にのみ対策を当てる（図の候補のまま
  対策しない）。
- **未確認の前提**: 各要因はまだ**要因候補**であり検証前。「摩耗が原因」と断定せず、データで裏を取ってから
  結論する（推測のまま進めない）。

## 相性（組み合わせると効く）

- `five-whys`: 特性要因図が**広さ（要因の網羅）**、なぜなぜ分析が**深さ（各枝を真因まで掘る）**。手順⑤の
  各骨に当てて掘り下げる定番の組合せ。
- `mece`: 大骨（カテゴリ）が**漏れなくダブりなく**なっているかを検算し、完全性の錯覚と抜けを防ぐ。
- `logic-tree`: 同じ「分解」の思想。原因追究型ロジックツリー（Whyツリー）と相互補完でき、構造の妥当性を高める。
- `qc-story`: QCストーリー／DMAICの「要因解析」ステップの中核ツールとして組み込む（前後に現状把握・対策・
  歯止めが並ぶ）。
- `brainstorming`: 手順④の要因出しを活性化する発散手法。判断保留で候補数を稼ぐ（原因列挙型と好相性）。
- 揺さぶり枠として `devils-advocate`（「本当にその要因が主因か？別の説明は？」と最有力候補を疑う）や
  `premortem`（対策が失敗する要因を先回りで洗い出す）を添えると、思い込みによる誤診を減らせる。
- 洗い出した要因の**優先順位づけ**には `payoff-matrix` / `decision-matrix`（効果×実現性で対策を選ぶ）へ接続。
