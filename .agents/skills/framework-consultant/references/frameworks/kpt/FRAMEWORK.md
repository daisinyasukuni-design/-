# KPT（ふりかえり）

## 概要

KPTは、チーム（または個人）の一定期間の活動を **Keep / Problem / Try** の3枠でふりかえり、
**軽い対話から「次に試す具体的な一手(Try)」を生み出し、次サイクルで検証して改善を累積する** 手法。
アジャイル/スクラムの定例レトロスペクティブで最も広く使われる型の1つ。

| 枠 | 書くこと | 性質 | 次への働き |
|---|---|---|---|
| **Keep（続ける）** | 良かったこと・うまくいって今後も続けたいこと | 事実（正の側面） | 伸ばす施策の種になる |
| **Problem（問題）** | 困っていること・うまくいかないこと | 事実（負の側面） | 解決策の種になる |
| **Try（試す）** | 次サイクルで試す具体的アクション | 打ち手（未来） | 次回に実行→検証する |

- **核となる考え方**: まず起きた事を「続けたい(Keep)」「困っている(Problem)」という**事実**に分け、
  そこから**未来の行動(Try)**を1〜数個生む。Try は「Problemを解く」だけでなく「Keepをさらに伸ばす」からも出る。
  Try を次サイクルで実行・検証し、定着したら Keep へ、残った問題は Problem へ回す——この**累積更新**が本質。
- **軽さが価値**: 重い計画文書や定量目標を前提とせず、ホワイトボードと付箋で全員が短時間で回せる。
  小チームの定例に最初に導入する改善の型として機能する。
- **事実(K/P)と打ち手(T)の分離**: 感情的な反省会・犯人探しに陥らせないため、まず事実を並べ、
  そのうえで前向きに次の行動へ変換する。リーダーが一方的に書かず、全員参加のブレスト形式で行う。
- **出自（要確認）**: 原型は **Alistair Cockburn** の **Reflection Workshop**（Crystal 方法論群、『Crystal Clear』2004）。
  これを日本に伝え **「KPT」と命名・簡略化したのが平鍋健児**（永和システムマネジメント、2005年のブログ）。
  **天野勝**が書籍『これだけ! KPT』(2013)で普及させた。より包括的な **Derby & Larsen のふりかえり5段階**(2006)の
  中では、KPTは「データを集め洞察を得て次を決める」アクティビティに位置づく（→出典/要確認）。

## いつ使う / 使わない

**使う（適する状況）**
- スプリント末・週次・月次など、**定例のふりかえり**を軽く回したいとき。
- チームの**改善が回っていない/形骸化している**、反省会が愚痴や犯人探しで終わってしまうとき。
- 良かった点と課題を棚卸しして、**次に試す具体的な一手**をチームで合意したいとき。
- アジャイル/スクラムのレトロスペクティブを、誰でも回せる**型に落としたい**とき。
- 大掛かりな改善プロジェクトを立てる前に、**小さく改善を積み上げ**て手応えを作りたいとき。
- 個人の週次ふりかえり（1人KPT）で、習慣や仕事の進め方を軽く点検したいとき。

**使わない / よくある誤用（アンチパターン）**
- **指標・標準化を伴う本格的な業務改善に単独で使う**——定量目標の設定・計画・工程管理・横展開まで要る改善は pdca、
  厳密な問題解決手順が要るなら qc-story の領域。KPTは軽量な定性ふりかえりで、そこまで背負わせない。
- **Problem偏重で後ろ向きになる**——最頻の誤用。「課題を出さねば」の空気でProblemに議論が偏り、Keepがおまけ扱いになる。
  Keep（良かったこと）を先に十分出し、前向きな場を保つ。
- **Tryが抽象的で検証できない**——「気をつける」「頑張る」「意識する」はTryではない。**誰が・いつ・何をするか**が
  分かる具体アクションにし、次回に結果を測れる形にする。
- **真因を掘らずに対症療法**——表層のProblemに表層のTryを当てると再発する。効きそうな所は five-whys で真因まで下ろす。
- **前回Tryをやりっぱなしにする**——検証しないと形骸化する。毎回**冒頭で前回Tryの結果をレビュー**し、K/Pへ回す。
- **心理的安全がないまま強行する**——声の大きい人や上下関係で本音が出ないと機能しない。発言の否定禁止・匿名付箋などで場を作る。
- **Tryを盛りすぎる**——一度に多数のTryは実行されず流れる。次サイクルで回せる少数（目安1〜3個）に絞る。

## 前提と限界

- **前提**: (1) **ふりかえる対象期間と単位**（このスプリント／今週／このプロジェクト）が定まっていること。
  (2) 参加者が事実を**率直に出せる心理的安全**があること（無ければまず場づくり）。
  (3) 次サイクルが存在し、**Tryを実行・検証できる継続的なリズム**があること（単発では改善が累積しない）。
  対象や場が曖昧なら壁打ちで補い、継続リズムが無いなら定例に組み込む設計を先に決める。
- **限界（批判を踏まえて）**:
  - **Problem偏重の構造的傾向**——枠組み上、問題探しに流れKeepとTryが痩せやすい。意図的にKeepと前向きTryを引き出す運営が要る。
  - **深掘りの弱さ**——3枠に並べるだけでは真因に届かない。要因分析(five-whys)や上位の改善サイクル(pdca)の補助が要る場面がある。
  - **定量に弱い**——満足度や指標の測定・目標管理は守備範囲外。効果測定は kgi-kpi-okr 等に接続する。
  - **アクションの実行保証がない**——Tryを出しても実行・検証を回す仕組み（担当・次回レビュー）を別途組まないと空回りする。
  - **ファシリテーション依存**——場の作り方・引き出し方で成否が大きく変わる。テンプレだけでは機能しない。
  - **上位プロセスの一部にすぎない**——Derby & Larsen の5段階（場を設定→データ収集→洞察→次を決定→締め）の中の
    データ収集〜意思決定を担う一手法。場の設定と締めは別途要る。
- これらは、**真因深掘りを five-whys で、本格改善サイクルを pdca/qc-story で、指標接続を kgi-kpi-okr で、
  盲点の揺さぶりを devils-advocate/premortem で** 補って埋める（→相性）。

## 進め方（手順）

命令形で示す。各ステップに「なぜ」を添える。**事実(K/P)を先に並べ、そこから未来の行動(T)へ変換する**のが肝。

1. **対象期間と場を設定する。** 何をふりかえるか（このスプリント／今週）とゴール（改善アクションを1〜3個決める）を宣言し、
   発言を否定しない・犯人探しをしない、という場のルールを共有する。
   なぜ: 範囲と安全が決まらないと、事実が率直に出ず対話が愚痴か沈黙に振れる。まず土俵と空気を作る。
2. **前回のTryをレビューする（2回目以降）。** 前サイクルのTryが実行されたか・効果が出たかを確認する。
   なぜ: 検証しないTryは形骸化する。定着したTryはKeepへ、残った問題はProblemへ回し、改善を累積させる起点にする。
3. **Keepを出す。** 良かったこと・うまくいって今後も続けたいことを、各自が付箋に書き出して貼り、共有する。
   なぜ: 先に正の事実を並べると場が前向きになり、Problem偏重を防げる。続けたい強みはTry（伸ばす施策）の種にもなる。
4. **Problemを出す。** 困っていること・うまくいかないことを、同様に各自書いて貼り、共有する。
   なぜ: 負の事実を個人の主観でなくチームの共有事実にすることで、非難でなく改善対象として扱える。
5. **K/Pの真因を掘る。** 似た付箋をグルーピングし、「なぜそれが起きたか」を問う。効きそうな重要Problemは five-whys で下ろす。
   なぜ: 表層のまま対策すると再発する。真因に当てたTryほど効く。全部は掘らず、重い所に絞る。
6. **Tryを生む。** 「Problemを解く施策」と「Keepをさらに伸ばす施策」の両方からアイデアを出す。
   なぜ: Tryは問題解決だけのものではない。強みの強化も改善であり、前向きな一手が生まれる。
7. **Tryを絞り、具体アクションにする。** 次サイクルで実行可能な少数（目安1〜3個）に絞り、**誰が・いつ・何をするか**、
   次回に何で成否を判断するかまで決める。「気をつける」等の抽象語は具体行動に書き換える。
   なぜ: 実行と検証ができないTryは流れる。次回レビューできる粒度にして初めて改善が回る。
8. **記録し、次サイクルに引き継ぐ。** ボードを保存/掲示し、決めたTryと担当を残す。次回の冒頭でここから再開する。
   なぜ: KPTの価値は単発の気づきでなく累積更新。前回の続きから回すことでチームの改善が積み上がる。

## 壁打ち質問リスト

各枠を事実で埋め、Tryを具体化するために、利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す。

1. このふりかえりで**最終的に決めたいこと**は何ですか？（次に試す改善アクションの決定／課題の棚卸し／チームの状態点検）
2. ふりかえる**対象期間と単位**は何ですか？（このスプリント／今週／このプロジェクト——範囲を1つに絞れますか）
3. **前回のTry**はありますか？実行され、効果は出ましたか？（無ければ初回として進めます）
4. この期間で**良かったこと・続けたいこと（Keep）**は何ですか？（先に強みを出します——小さなことでも構いません）
5. **困っていること・うまくいかないこと（Problem）**は何ですか？それは「なぜ」起きていますか？（真因まで言えますか）
6. そのProblemのうち、**今サイクルで最も効かせたい一件**はどれですか？（全部は掘りません——重い所に絞ります）
7. Keepを**さらに伸ばす**としたら、何を試せますか？（Tryは問題解決だけでなく強みの強化からも出します）
8. 出したTryを**誰が・いつ・何をするか**まで言えますか？「気をつける」でなく具体的な行動に落とせますか？
9. 次回、そのTryの成否を**何で判断**しますか？（実行できたか／どんな変化が見えたか）
10. この場は**本音を出せる状態**ですか？（発言しづらい／声の偏りがあるなら、匿名付箋や進行の工夫が要ります）

## 出力フォーマット

ALWAYS この型で出力する（3枠の整理 → 具体化したTryと次サイクル）。型を固定し、常にこの構造で返すこと。

```
【KPT】対象期間: <スプリント/週など> ／ 目的: <決めたいこと> ／ 場: <心理的安全・ルールの状態>

【前回Tryのレビュー】（2回目以降）
  - <前回Try>: 実行=<済/未> 効果=<所見> → <Keepへ昇格/継続Problem/クローズ>

【Keep（続ける）】   - <良かった・続けたい事実>（なぜ効いたか）…
【Problem（問題）】  - <困っている事実>（真因の仮説: なぜ起きたか）…
【Try（次に試す）】
  1. <具体アクション>  担当: <誰>  時期: <いつ>  検証: <次回に何で成否を見るか>  由来: <解くProblem / 伸ばすKeep>
  （※次サイクルで回せる少数=目安1〜3個に絞る。「気をつける」等の抽象語は禁止）

【次の一手】<最優先で実行するTry・次回冒頭でレビューする項目を1〜3個>
【未確認の前提】<Problemの真因が仮説どまり／Tryの効果が未検証／場の心理的安全／継続リズムの有無——裏取りが要る点>
```

## 具体例（ワークスルー）

対象を一般化した例（架空の企業名・数値は用いない）。あるソフトウェア開発チームが、
**2週間スプリント末の定例ふりかえり**を回す場面。

- **手順①場の設定**: 対象=直近スプリント、目的=「次スプリントで試す改善を2個決める」、ルール=否定しない・犯人探しをしない、を宣言。
- **手順②前回Tryレビュー**: 前回Try「デイリーを15分で切る」は実行され会議時間が短縮 → Keepへ昇格。
  前回Try「レビュー依頼を早める」は未実行 → 継続Problemへ戻す。
- **手順③Keep**: ペア作業で早期にバグを発見できた／朝会が時間内に収まった、を各自付箋で共有。
- **手順④Problem**: スプリント終盤にレビュー待ちのタスクが滞留した／仕様の認識が途中でずれた、を共有。
- **手順⑤真因を掘る**: 「レビュー滞留」を five-whys で下ろすと、レビュー依頼が終盤に集中する運用が真因、と仮説化。
- **手順⑥Try生成**: Problem由来=「レビュー依頼のタイミングを分散する」、Keep由来=「早期バグ発見が効いたペア作業を対象タスクを広げて続ける」。
- **手順⑦具体化・絞り込み**: Tryを2個に絞る。(1)「タスク完了ごとに即レビュー依頼を出す運用を全員で試す」担当=チーム全員/次スプリント、
  検証=終盤の滞留件数が減ったか。(2)「難所タスクは着手時にペアを組む」担当=各担当/都度、検証=手戻り件数。
  「気をつける」等の抽象語は排し、行動と検証条件まで固定。
- **手順⑧記録・引き継ぎ**: ボードを保存し、次スプリント冒頭でこの2つのTryのレビューから再開すると決める。
- **次の一手**: (1)の即レビュー依頼運用を最優先で実行し、次回冒頭で滞留件数を確認する。
- **未確認の前提**: 「レビュー依頼の集中が真因」はまだ仮説。次サイクルの実データで裏取りが要る。心理的安全は良好だが新メンバーの発言量は要観察。

## 相性（組み合わせると効く）

- `pdca`: KPTで出した改善を、指標・標準化まで含めた本格的な改善サイクルに載せ替える上位の受け皿。KPT（軽い定性）→PDCA（重い管理）の順で重層化。
- `qc-story`: 重いProblemを厳密な問題解決手順（テーマ選定→現状把握→要因解析→対策→効果確認→標準化）で解く、KPTより本格的な続き。
- `five-whys`: KPTのProblemの真因を掘り下げ、表層Tryによる対症療法を防ぐ直接の深掘りツール。
- `grow-model`: 個人の目標達成コーチング（目標→現実→選択肢→意志）。チーム定例のKPTに対し、個人の行動変容を扱う隣接手法。
- `kgi-kpi-okr`: Keep=守る指標／Problem・Try=伸ばす指標、とふりかえりを定量目標・KPI設計に接続する後工程。
- `service-blueprint`: 業務やサービス提供のプロセスを可視化した上でKPTを回すと、Problem/Tryを工程のどこに効かせるか精緻化できる。
- 揺さぶり枠として `devils-advocate`（「このTryで本当に効くのか」を疑う）、
  `premortem`（決めたTryが次サイクルで失敗する筋を先回りで潰す）、`aarrr`（プロダクト文脈でどの指標段階の改善かを見立てる）を添えると打ち手が締まる。
