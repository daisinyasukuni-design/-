# ピラミッドストラクチャー

## 概要

ピラミッドストラクチャー（ピラミッド原則）は、伝えたい **結論を頂点** に置き、その下に
**根拠（キーライン）**、さらに下に **事実・データ** を積み上げて、思考と伝達を
「結論先行（トップダウン）」で構造化する論理構成技術。核となる主張は
**「明快な文章とは、明快な論理構成にほかならない」**——読み手は、1つの主メッセージの下に
ピラミッド状に整理された考えなら容易に理解できる、という前提に立つ。

```
                 [結論] ← 読み手の問い(Q)への答え・ピラミッドの頂点
            ┌───────┼───────┐
        [根拠A]   [根拠B]   [根拠C] ← キーライン（同種・MECE・順序づけ）
        ┌─┴─┐    ┌─┴─┐    ┌─┴─┐
       事実 事実  事実 事実  事実 事実 ← データ・分析による裏付け
```

- **縦の論理（vertical）**: 上位メッセージは読み手の頭に「なぜ？／本当か？」という疑問を生み、
  直下のメッセージ群がそれに答える問答が縦に連鎖する。上→下は **Why So?（なぜそう言える？＝検算）**、
  下→上は **So What?（だから何？＝要約・統合）** の関係で結ばれていなければならない。
- **横の論理（horizontal）**: 同じ階層のメッセージは **MECE（漏れなく・ダブりなく）** で、
  **同じ種類・同じ抽象度** で、論理的に順序づけられている。結び方は2種類——
  **演繹**（大前提→小前提→ゆえに結論、と逐次連鎖／"therefore"）か、
  **帰納**（同種の並列した根拠を1つのSo Whatでまとめる）。
- **導入部（SCQA）**: 頂点の結論に読み手を連れて行く前ふり。
  **状況(Situation)→複雑化(Complication)→疑問(Question)→答え(Answer=頂点)** の物語で問いを立てる。
- **出自（要確認扱い）**: 考案者は **Barbara Minto（バーバラ・ミント）**。Harvard MBA(1963)、
  McKinsey が採用した最初の女性MBAコンサルタントとされ、コンサルの文章・提案の構成改善のために開発した。
  **MECE の考案者**でもある。書籍『The Pyramid Principle』（初版年は資料で食い違う: Wikipedia=1985／本人サイトは「1987執筆」と記載／Internet Archiveに1981年Minto International版＝要確認）、
  拡張版『The Minto Pyramid Principle』(1996)、日本語版『考える技術・書く技術』（→出典・要確認参照）。

## いつ使う / 使わない

**使う（適する状況）**
- **報告・提案・プレゼン・メール・エグゼクティブサマリの構成**を、結論先行で一発で伝わる形に組みたいとき。
- 多忙な **意思決定者に「で、何が言いたい？」を最初に**届け、根拠は必要な人だけ掘れる形にしたいとき。
- **書く前・話す前に自分の思考を整理**したいとき（構造化＝思考の検算になる）。
- 「話が飛ぶ／長い／根拠が弱い」と言われる、**主張と根拠のつながりを点検**したいとき。
- 資料や文書の **骨子（ストーリーライン）を先に固めてから**肉付けしたいとき。

**使わない / よくある誤用（アンチパターン）**
- **グルーピングで止まり "So What" が無い**——最頻の失敗。「3つの課題」のような**カテゴリ見出し（並べただけ）**で終わり、
  「だから何が言えるのか」という**統合メッセージ**になっていない。Mintoは grouping（羅列）と synthesizing（要約）を峻別する。
- **Why So? が通らない（論理の飛躍）**——頂点の結論が、下の根拠から本当には導けていない。見た目の三角形は綺麗でも中身が崩れる。
- **横がMECEでない／同種でない**——1グループに抽象度や種類の違う要素を混ぜる（「売上」と「担当者のやる気」を並列にする等）。
- **イシュー（頂点の問い）のズレ**——相手の問い≠自分の問い だと、論理が完璧でも**的外れ**になる。まず問いを合わせる。
- **データ過多 / boil the ocean**——論点に無関係な分析を積み、洞察が埋もれる。ピラミッドは結論に効く事実だけを残す装置。
- **感情・信頼の軽視**——論理(logos)偏重で、共感(pathos)や語り手の信頼(ethos)を欠くと機械的で刺さらない。説得は論理だけではない。
- **探索・発散・共創の段階には不向き**——アイデア出しやデザイン思考の発見フェーズで硬直的な三角形を課すと、反復と発見を殺す。
- **化粧的採用**——分析の質を伴わないまま体裁だけピラミッド化しても、精査で崩れる。構造は中身の代わりにならない。

## 前提と限界

- **前提**: (1) 答えるべき **問い（イシュー）が1つに定まっている**こと。問いが曖昧だと頂点が決まらず羅列に堕ちる。
  (2) 頂点を支える **事実・根拠がある程度そろっている**こと（無ければ壁打ち／調査で埋める。構造化は分析の代わりにならない）。
  (3) 読み手が誰で、何を既に知っているかが分かること（導入部SCQAの出発点になる）。
- **限界（批判を踏まえて）**:
  - **論理(logos)に偏りやすい**——説得の3要素（ethos/pathos/logos）のうち感情・信頼を扱わない。機械的・engineered に見えるとの批判がある。
  - **構造は中身を保証しない**——立派なピラミッドでも、前提や事実が誤っていれば結論は誤る。GIGO（入力が悪ければ出力も悪い）。
  - **硬直性**——探索・共創・反復が本質の場面では、確定した結論を先に置く形式が発想や合意形成を阻害しうる。
  - **要約の主観**——「So What」の一言に何を選ぶかで結論が変わる。恣意的な要約は論理を装った誘導になりうる。
- これらは、**頂点の主張を devils-advocate / premortem で叩く / 横の漏れダブりを mece で検査する /
  根拠の深さを five-whys・logic-tree で補強する**ことで緩和できる（→相性）。

## 進め方（手順）

命令形で示す。各ステップの「なぜ」を添える。トップダウン（問い→仮説→検算）を基本に、材料が生煮えならボトムアップ（事実→グルーピング→要約）を併走させる。

1. **読み手と問い（イシュー）を1つに固定する。** 「誰に、どの問いへの答えを届けるのか」を明文化する。
   なぜ: 頂点は「読み手の問いへの答え」。問いがズレると、以降の論理が完璧でも的外れになる（最大の失敗）。
2. **導入部（SCQA）で問いを立てる。** 状況(S: 読み手が同意する既知の事実)→複雑化(C: 状況を揺るがす変化)→疑問(Q)→答え(A) を並べる。
   なぜ: いきなり結論をぶつけるのでなく、読み手の頭に「その問い」を先に立てると、頂点が"待たれた答え"になる。
3. **頂点の結論（主メッセージ）を1文で言い切る。** Qへの直接の答えを、動詞のある完全な主張で書く（「〜の3点」等の名詞句で逃げない）。
   なぜ: 頂点が曖昧だと下位が発散する。まず仮説でよいので言い切り、後で検算する（完璧主義で止めない）。
4. **キーライン（根拠）を並べる。** 頂点を支える根拠を、同じ種類・同じ抽象度で、MECEに数個（目安3つ前後）挙げる。
   なぜ: 種類が混ざる／漏れダブりがあると横の論理が崩れる。人が一度に扱える数に絞ると伝わる。
5. **各根拠を事実・データで裏付ける。** キーラインの下に、その根拠を成り立たせる具体的事実・分析を置く。
   なぜ: 根拠は「なぜそう言える？」に答える証拠を伴って初めて成立する。ここが薄いと精査で崩れる。
6. **縦を Why So? / So What? で検算する。** 上→下に「Why So?（なぜそう言える？）」、下→上に「So What?（だから何？）」を問い、
   どちらも通るか確認する。So Whatが**カテゴリ見出し（並べただけ）**でなく**統合メッセージ**になっているかを特に見る。
   なぜ: 縦がつながらないピラミッドは、論理の飛躍か、要約の失敗。ここが本フレームの心臓部。
7. **横を MECE と結び方（演繹/帰納）で検算する。** 各グループが漏れダブり無く、演繹（逐次連鎖）か帰納（並列を1つに要約）で
   一貫して結ばれているかを確認し、順序（時間／構造／比較／演繹）を整える。
   なぜ: 横が崩れると「同じ土俵で比べていない」印象を与える。Mintoは順序づけの欠如を強く戒める。
8. **読み手に合わせて出力する。** トップダウン（結論→根拠→事実）で書き、深さは相手のリテラシー・関心に合わせて調整する。
   なぜ: ピラミッドは思考の道具であると同時に、伝達の順序でもある。相手が掘りたい枝だけ掘れる形が最も速く伝わる。

## 壁打ち質問リスト

各要素を事実で埋めるために、利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す。

1. この文書・話は **誰に届けますか**？その相手は前提として**何を既に知っていて**、何を気にしていますか？（導入部Sの起点）
2. 相手が抱く（べき）**問いは一言で何**ですか？「この報告で相手に判断・行動してほしいこと」は何ですか？（頂点の問いを1つに）
3. その問いへの **あなたの結論（答え）を、動詞のある1文**で言い切ると？（名詞句「〜の課題」で逃げず、主張の形に）
4. その結論を **なぜそう言えるのか（Why So?）**、支える根拠を挙げてください。根拠どうしは**同じ種類**ですか？**漏れやダブり**はないですか？
5. 各根拠は **どの事実・データ・分析**で裏付けられますか？「印象・推測」と「確認済みの事実」を分けると、どこが未確認ですか？
6. 根拠を上から読むと結論に、下から読むと **「だから何（So What?）」に本当につながりますか**？途中で飛躍していませんか？
7. 相手が最初に抱きそうな **反論・疑問は何**ですか？それはピラミッドのどこ（どの根拠・事実）で受け止められていますか？
8. 状況(S)から結論(A)へ、相手を動かす **複雑化(C＝なぜ今この問いなのか)** は何ですか？（前ふりが無いと結論が唐突になる）

## 出力フォーマット

ALWAYS この2段構えで出力する（導入部で問いを立てる → ピラミッド本体＋縦横チェック）。命令形テンプレを埋める。

```
【導入部(SCQA)】読み手: <誰> ／ 問い(Q): <相手に答える1つの問い>
  S(状況):    <読み手が同意する既知の事実>
  C(複雑化):  <状況を揺るがす変化＝なぜ今この問いか>
  Q(疑問):    <Cから自然に生じる問い>

【ピラミッド本体】
  ■結論(A/頂点): <Qへの答えを、動詞のある1文で言い切る>
    ├─根拠A: <同種・MECE>  ┐
    │    └事実: <裏付けデータ・分析>  │ 各根拠は Why So? に答える
    ├─根拠B: <同種・MECE>  │ 事実を伴う
    │    └事実: <…>        │
    └─根拠C: <同種・MECE>  ┘
         └事実: <…>
  結び方: <演繹 / 帰納 のどちらか>（帰納なら根拠群を括る複数名詞＝「理由/条件/打ち手」等を明記）

【縦横チェック】
  Why So?（上→下）: <各根拠が結論を本当に支えているか＝飛躍の有無>
  So What?（下→上）: <根拠群が"カテゴリ見出し"でなく統合メッセージに要約されているか>
  MECE（横）: <漏れ・ダブり・種類の不一致がないか>

【次の一手】<この骨子を文書/プレゼンに肉付けする・不足根拠の追加調査・レビュー相手>
【未確認の前提】<印象・推測に留まり、事実確認が要る点（壁打ちで埋める）>
【想定反論と受け】<相手の主な反論と、それをどの根拠で受けるか>
```

## 具体例（ワークスルー）

対象を一般化した例（架空の数値・企業名は用いない）。ある担当者が、主力サービスの
**問い合わせ対応の残業が慢性化**している状況について、上長に対応方針を報告する場面。

- **手順①読み手と問い**: 読み手=決裁権を持つ上長。問い=「この残業に、何をどう手当てすべきか」。
- **手順②導入部(SCQA)**:
  - S(状況): 問い合わせ対応チームは長く安定運用されてきた。
  - C(複雑化): 直近で問い合わせ件数が増え、残業が常態化して離職の兆しが出ている（＝今この問いが必要な理由）。
  - Q(疑問): 残業を減らしつつ対応品質を保つには、何をすべきか。
- **手順③頂点(結論)**: 「**問い合わせの"発生"を減らす施策を最優先し、増員は補助にとどめるべき**」と1文で言い切る（仮説）。
- **手順④キーライン（根拠・MECE・同種）**: 「なぜ発生削減が先か」を3つの同種の理由で支える。
  - 根拠A: 増員は残業の**症状**を緩和するが、件数という**原因**は減らない。
  - 根拠B: 問い合わせの多くは**特定の少数パターンに集中**しており、発生源を絶てる余地が大きい。
  - 根拠C: 発生削減は**恒久的にコストを下げる**が、増員は固定費を増やし続ける。
- **手順⑤事実で裏付け**: 各根拠の下に、問い合わせログの分類・時系列、離職の兆候、コスト構造などの
  **確認済みデータ**を置く（推測は下の「未確認」へ回す）。
- **手順⑥縦チェック**: Why So?→「なぜ発生削減が先か」に3根拠が答えている。So What?→3根拠は
  「増員より発生削減が本質的」という**統合メッセージ**に要約される（"3つの論点"という見出しで止めない）。
- **手順⑦横チェック**: 3根拠は「発生削減を優先すべき理由」という同種で括れる（**帰納**）。原因/症状/コストで
  種類の重複がないかを確認（MECE）。順序は重要度順（比較）に並べる。
- **次の一手**: この骨子（結論＋根拠A/B/C）を報告資料に肉付けし、根拠Bの「少数パターン集中」をログ再集計で補強してから上長レビューにかける。
- **未確認の前提**: 「少数パターンに集中」という配分は実ログの再集計で裏取りが要る——推測のまま結論しない。
- **想定反論と受け**: 「まず増員では？」に対し、根拠A（症状対処）と根拠C（固定費増）で受ける。

## 相性（組み合わせると効く）

- `so-what-why-so`: ピラミッドの**縦の論理そのもの**（So What?で要約、Why So?で検算）。頂点と根拠のつながりを鍛える直接の相棒。
- `mece`: **横の論理**（キーラインの漏れ・ダブり・同種性）を検査する。ピラミッドの各グループはMECEが前提。
- `logic-tree`: 問題や要素を樹形に**分解**する道具。ピラミッドは"メッセージ版のロジックツリー"であり、分解の材料を供給する。
- `five-whys`: 根拠を「なぜ？」で掘り下げ、頂点を支える**真因ベースの事実**を厚くする（特に原因分析型の報告で）。
- 導入部（SCQA）は本スキル内に含むが、頂点の問い自体が難しいときは `logic-tree` で論点を分解してから頂点を立てるとよい。
- 揺さぶり枠として `devils-advocate`（頂点の結論をあえて否定し、根拠の弱点を炙る）や
  `premortem`（結論通り動いた結果失敗する筋を先回りし、抜けた根拠・前提を発見）を1つ添えると、論理の飛躍と独断を潰せる。
