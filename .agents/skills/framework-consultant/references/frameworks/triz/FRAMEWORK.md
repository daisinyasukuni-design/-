# TRIZ（発明的問題解決の理論）

## 概要

TRIZ（トリーズ、露: Teoriya Resheniya Izobretatelskikh Zadach ＝「発明的問題解決の理論」）は、
**膨大な特許・発明を分析し、分野を超えて再発する"発明のパターン"を抽出した**発想支援の体系。
核心は次の3点。

- **発明は少数の普遍パターンに帰着する** — 別業界の解が自分の問題にそのまま効く。ゼロから閃かず、蓄積を引く。
- **良い発明は矛盾（トレードオフ）を"妥協せず"克服する** — 「AもBも欲しいが両立しない」を、折衷ではなく突破する。
- **系は理想性（Ideality）に向かって進化する** — 「機能はそのまま、コスト・害はゼロ」に近づける方向で解を探す。

**共通の解き方（TRIZのプリズム）**: 目の前の固有問題をそのまま解こうとせず、
① **一般化**して「標準問題（矛盾/機能モデル）」に写像 → ② 蓄積された**標準解**（原理・標準解集）を当てる →
③ それを自分の文脈へ**具体化**して固有解に翻訳する。この「抽象化して借りて、翻訳し戻す」往復がTRIZの背骨。

- **出自（要確認・断定回避）**: 考案者は **ゲンリッヒ・アルトシューラー**（ソ連の発明家・SF作家）。
  1946年頃、海軍の発明審査部門で特許を評価するなかで着想したとされる。多数の特許を分析して普遍原理を抽出した、
  という点は各資料で一致するが、**分析した特許数（数万〜数十万で資料が食い違う）や年号は要確認**（→出典）。

**このスキルは大物。** TRIZは5つのサブツールを内包する。FRAMEWORK.md本体は「概要＋どのサブツールをいつ使うか＋壁打ち」に絞り、
各ツールの詳細な一覧・手順は `references/` に置く。**まず本体で診断し、必要なサブツールの reference を読み込んで適用する**。

| サブツール | 一言 | いつ使う | 参照 |
|---|---|---|---|
| 40の発明原理 | 矛盾を解く普遍的な発想の型40種 | 矛盾がある/なくても発想の種が欲しい | `references/principles-40.md` |
| 矛盾マトリクス | 技術的矛盾→有望な原理の逆引き表 | 「Aを上げるとBが下がる」を型で当てたい | `references/contradiction-matrix.md` |
| 物質-場分析 | 機能をS1-S2-場でモデル化し標準解へ | 機能が不足/有害/過剰。何が足りないか診たい | `references/su-field.md` |
| 9画面法 | 空間×時間の3×3で系を俯瞰 | 問題を系全体・時間軸で捉え直したい | `references/nine-windows.md` |

## いつ使う / 使わない

**使う（適する状況）**
- **技術的トレードオフを両立させたい**とき（軽量化↔強度、速度↔精度、コスト↔品質、小型化↔容量 など）。
- 既存設計の**改善が頭打ち**で、延長線上でない別解・ブレイクスルーが欲しいとき。
- **不良・機能不全**の対策アイデアを、思いつきでなく構造的に洗い出したいとき（有害機能の除去）。
- **特許回避 / 迂回設計** — 同じ機能を別原理で実現する代替案を系統的に探したいとき。
- 製品・プロセス・装置など**技術的対象**で、発想の網羅性と再現性を上げたいとき。

**使わない / よくある誤用（アンチパターン）**
- **矛盾を定義せず原理を"つまみ食い"** — 最頻の失敗。40原理を眺めて当てずっぽうに選ぶのはTRIZではない。
  まず「何と何が両立しないのか（矛盾）」を言語化し、一般化してから原理へ写像する。
- **一般化・具体化を飛ばす** — マトリクスが出した原理番号を"答え"にしてしまう。原理は**種**であり、
  自分の文脈への翻訳（③具体化）が本番。ここを省くと使えないアイデアの羅列になる。
- **マトリクスを万能視する** — アルトシューラー自身が後年、矛盾マトリクスを比較的非効率と見なし、
  ARIZや物質-場/標準解へ軸足を移したとされる（要確認だが重要）。マトリクスは入口で最も普及するが、
  **空欄セルがある／各セル最大4原理しか示さない／現実の多様な特性を39に押し込む写像ギャップ**という限界を持つ。
  行き詰まったら物理的矛盾＋分離原理、物質-場、9画面へ切り替える。
- **非技術問題への安易な適用** — 本流は工学・技術。対人・組織・市場・純粋な感性デザインには直接は不向き
  （拡張版はあるが、まずは他フレームを検討）。
- **習熟前に速答を求める** — ツール群が多く抽象的。時間が無い/矛盾が無い発散なら、ブレストやSCAMPERが速い。

## 前提と限界

- **前提**: 対象が**技術的に記述できる**こと（部品・機能・パラメータで語れる）。改善したい特性と、
  それが犠牲にする特性が**トレードオフの形で言える**とTRIZが最も効く。矛盾がまだ曖昧なら壁打ちで抽出する。
- **限界（批判を踏まえて）**:
  - **抽象化ギャップ** — 固有問題を39パラメータや標準問題へ写像する所に主観と技量が要る。写像を誤ると解も外れる。
  - **過去発明ベース** — 蓄積は既存特許由来。真に前例のない領域では原理が示唆に留まる。
  - **学習コスト** — 40原理・76標準解・ARIZなど道具立てが多く、習熟に時間がかかる。まずは40原理＋分離原理＋9画面から。
  - **技術偏重** — 人間・組織・市場の問題には土俵が合わない。
- これらは、**矛盾を丁寧に定義する／マトリクスに頼り切らず物理的矛盾と分離原理・物質-場・9画面を併用する／
  出た原理を必ず具体化して検証する**ことで補える（→相性・手順）。

## 進め方（手順）

命令形で示す。各ステップの「なぜ」を添える。詳細な一覧・手順は該当 reference を読み込んで使う。

1. **問題を機能とパラメータで書き出し、矛盾を1つに特定する。** 「何を良くしたいか（改善特性）」と、
   「それを追うと何が悪化するか（悪化特性）」を言語化する。なぜ: TRIZは矛盾を入口にする。矛盾が無いなら本ツールより発散法が速い。
2. **矛盾のタイプを見極める。** 別々の特性が衝突＝**技術的矛盾**、同一要素に相反する要求＝**物理的矛盾**。なぜ: タイプで使う道具が変わる（次項）。
3. **一般化して標準解へ写像する（対象に応じてサブツールを選ぶ）。**
   - 技術的矛盾がはっきり → **矛盾マトリクス**で39パラメータに翻訳し、交点の原理候補を引く（`contradiction-matrix.md`）。
   - 矛盾が曖昧/発想の種が欲しい → **40の発明原理**を刺激として一通り当てる（`principles-40.md`）。
   - 物理的矛盾（同一要素が相反） → **分離原理**（空間/時間/条件/部分-全体で分離）で相反を解く。
   - 機能が不足/有害/過剰 → **物質-場分析**でS1-S2-場をモデル化し、標準解で欠けた要素を補う（`su-field.md`）。
   - 問題の捉え方自体を広げたい → **9画面法**で上位/下位システム×過去/現在/未来に視野を展開（`nine-windows.md`）。
   - 短時間で一気通貫に回したい → **USIT**の流れに乗せる（`usit.md`）。
   なぜ: 固有問題を直接解くと発想が枯れる。抽象の階段を一段上げて「借りられる解」に接続する。
4. **理想性（IFR）を描いて解の方向を定める。** 「コスト・害ゼロで機能だけが実現する理想像」を先に言葉にする。なぜ: 妥協解に流れず、突破の当たりを付けられる。
5. **原理・標準解を自分の文脈へ具体化する（最重要）。** 引いた原理番号を、対象の部品・工程・材料に**翻訳**して複数の具体アイデアに落とす。なぜ: 原理は種。翻訳を省くと使えない一般論で終わる（最頻の失敗）。
6. **アイデアを実現性で絞り、新たな副作用（二次矛盾）を点検する。** 有望案を選び、それが生む次の矛盾を洗う。なぜ: 一つ解くと別の矛盾が出るのが常。ループさせて質を上げる。
7. **検証すべき仮説・試作・次の一手に落とす。** 出た案から実験/試作/意思決定を1〜3個決める。なぜ: TRIZは発想の起点。作って終わりにしない。

## 壁打ち質問リスト

各要素を事実で埋めるために、利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す。

1. 解きたい問題は何ですか？ その対象を**部品・機能・工程の言葉**で言うと、どんな仕組みで動いていますか？
2. **改善したい特性**は何ですか？（例: 軽くしたい／速くしたい／安くしたい／壊れにくくしたい）その数値目標はありますか？
3. それを追うと、**代わりに悪化してしまう特性**は何ですか？（＝技術的矛盾。「Aを上げるとBが下がる」の形にできますか）
4. あるいは、**同じ部品・要素が"AでもありAでない"相反する状態を同時に求められて**いませんか？（＝物理的矛盾。例: 熱くも冷たくもあってほしい）
5. これまで試した解決策と、それが**うまくいかなかった理由**は何ですか？（既存の延長を避けるため）
6. コストも害もゼロで**理想的に実現するとしたら**、どんな状態ですか？（＝IFR。何が"ひとりでに"起きてほしいですか）
7. この問題は**上位のどんな系の一部**で、**下位はどんな部品**から成りますか？ 過去・未来にどう変化しますか？（9画面の材料）
8. 変えてはいけない**制約**（規格・安全・コスト上限・使える材料や場＝機械/熱/化学/電気/磁気）は何ですか？

## 出力フォーマット

ALWAYS この型で出力する（矛盾の定義 → 一般化 → 原理/標準解 → 具体化 → 次の一手）。命令形で固定する。

```
【問題と理想像】対象: <技術対象> ／ 使ったサブツール: <40原理/マトリクス/物質-場/9画面/USIT>
  IFR（理想解）: <コスト・害ゼロで機能だけが実現する状態>

【矛盾の定義】
  タイプ: 技術的 / 物理的
  技術的矛盾: <改善したい特性> を上げると <悪化する特性> が下がる
  （物理的矛盾なら）同一要素 <X> が <性質A> と <非A> を同時に要求される

【一般化 → 引いた解の種】
  - <マトリクス: 改善パラメータ×悪化パラメータ → 原理#…> / <選んだ発明原理 #番号・名称>
  - （物質-場なら）S1:<対象> S2:<作用体> F:<場> の不足/有害 → 標準解の方向: <…>

【具体化アイデア（原理を対象へ翻訳）】重要順に
  1. <原理#→ 具体案（部品/工程/材料への落とし込み）> — 期待効果 / 想定副作用
  2. <…>
  3. <…>

【次の一手】<検証すべき仮説・試作・意思決定を1〜3個>
【未確認の前提／二次矛盾】<事実確認が要る点・新たに生じうる矛盾>
```

## 具体例（ワークスルー）

対象を一般化した例（架空の数値・企業名は用いない）。**保冷用の携帯容器**で「断熱を厚くするほど中身は冷えるが、
容器がかさばり重くなる」トレードオフを突破したい場面。

- **手順①矛盾の特定**: 改善＝保冷性能（断熱）、悪化＝容積/重量（携帯性）。
- **手順②タイプ**: 別々の特性が衝突 → **技術的矛盾**。（同時に「壁は厚くも薄くもあってほしい」と言い換えれば**物理的矛盾**にもなる。）
- **手順③一般化（マトリクス）**: 「改善したい特性≒温度/エネルギー損失の低さ」と「悪化する特性≒動く物体の体積・重量」に翻訳し、
  交点の原理候補を引く（例として **分割 / 動的性 / 相変化 / 複合材料** といった型が示唆される想定）。
  ※実際の原理番号は `references/contradiction-matrix.md` で該当セルを引いて確定する。
- **手順③'物理的矛盾→分離原理**: 「壁は薄い（携帯時）が厚い（保冷時）」を**時間で分離** → 使う時だけ厚くなる構造へ。
- **手順④IFR**: 「容器が重さゼロ・体積ゼロのまま、中身の温度だけが保たれる」を理想像に据える。
- **手順⑤具体化（原理を翻訳）**:
  - 分割/動的性 → 使用時に展開し収納時は畳める**折りたたみ断熱層**。
  - 相変化 → 断熱そのものを厚くせず、**相変化材（保冷剤）**に冷熱の保持を肩代わりさせ壁を薄く保つ。
  - 複合材料 → 薄くても断熱性の高い**多層/真空断熱材**に置換し、厚み↔断熱の矛盾を材料側で解消。
- **手順⑥絞り込み/二次矛盾**: 相変化材案は有望だが「事前冷却の手間」という二次的な使い勝手の矛盾が出る → そこを次に解く。
- **手順⑦次の一手**: 「薄い真空断熱＋相変化材」の組合せを試作し、同一重量での保冷時間という仮説を検証する。
- **未確認の前提**: 実際の断熱係数・相変化材の容量、コスト影響 — ここは実測・実データで裏取りが要る（推測のまま進めない）。

## 相性（組み合わせると効く）

- `scamper`: 40原理と近縁の発想チェックリスト。矛盾が曖昧で「まず種を増やしたい」段階の発散に併用。
- `osborn-checklist`: 強制発想の問いで、TRIZ前の問題の見つめ直し・アイデア量産に効く。
- `morphological-analysis`: 物質-場や属性で分解した後、要素の組合せを総当たりで広げる（発散の相方）。
- `equivalent-transformation`: 「本質を抽出し別領域へ移す」等価変換は、TRIZの一般化→具体化と同系。異分野解の借用を補強。
- `five-whys` / `fishbone`: 不良・機能不全のTRIZ適用前に、そもそもの真因・要因を構造化して矛盾を正しく設定する前工程。
- `premortem`（揺さぶり枠）: 出したブレイクスルー案の失敗要因を先回りし、二次矛盾を洗い出す検証の相方。
- `pmi` / `payoff-matrix`: 発散した具体アイデアを多面評価・実現性×効果で絞り込み、次の一手に収束させる。
