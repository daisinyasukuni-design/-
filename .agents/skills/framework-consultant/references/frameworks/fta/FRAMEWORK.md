# FTA（故障の木解析）

## 概要

FTA（Fault Tree Analysis／故障の木解析）は、**望ましくない事象（トップ事象）** を頂点に置き、
それを引き起こす原因を **AND / OR の論理ゲート** で上から下へ **演繹的（トップダウン）** に分解して、
故障の論理構造を木（ツリー）で可視化する信頼性・安全性解析手法。到達点は2つ——
**(定性)** どの原因の組み合わせがトップ事象を起こすか＝**最小カットセット**を洗い出すこと、
**(定量)** 各原因の発生確率からトップ事象の発生確率を計算し、弱点の効き所を測ること。

- **核となる考え方**: 「結果（トップ事象）」から「原因」へ**逆向きに**論理を辿る。単なる原因の列挙でなく、
  原因どうしの**論理関係（ANDで重なって初めて起きるのか、ORでどれか1つで起きるのか）**を明示する点が肝。
  この論理構造があるからこそ、確率計算と弱点の定量比較ができる。
- **2つのゲート（Boole論理由来）**:
  - **ORゲート**: 入力の**いずれか1つでも**起きれば出力が起きる（＝故障が伝わりやすい＝弱い）。
  - **ANDゲート**: 入力が**すべて同時に**起きたときだけ出力が起きる（＝冗長・多重防護＝強い）。
- **主な記号**: トップ事象／中間事象（四角）、**基本事象**（これ以上分解しない末端＝円）、
  **非展開事象**（情報不足でそれ以上展開しない＝菱形）、**外部・ハウス事象**（通常起きる/起きない条件＝家形）。
- **最小カットセット（MCS）**: 同時に起きるとトップ事象を起こす基本事象の組み合わせ＝**カットセット**のうち、
  どの1事象も取り除けない最小の組。**要素1個のMCS＝単一障害点（single point of failure）**が最も危険。
- **出自（要確認）**: **1962年、ベル研究所の H.A. Watson** が、米空軍の契約下で **Minuteman I ICBM の
  発射管制システム**を評価するために考案。**Boeing**（David Haasl ら）が拡張・普及させ、1965年の
  System Safety Symposium（シアトル）で注目。原子力の **WASH-1400（1975）**、米NRC の
  **NUREG-0492「Fault Tree Handbook」(1981)** で標準化され、航空宇宙・原子力・プロセス産業の定番となった。
  年号・固有名は→出典/要確認を参照。

## いつ使う / 使わない

**使う（適する状況）**
- **重大事故・システム全停止・重大クレーム**など、起きてはならない**単一の重大事象**が「なぜ起こりうるか」を
  論理的・網羅的に洗いたいとき。
- **単一障害点（ひとつ壊れると全体が止まる箇所）**を特定し、どこを冗長化・多重化すべきか決めたいとき。
- **複数の故障が重なって初めて起きる最悪事象**（一つひとつは軽微でも組み合わさると致命的）を防ぎたいとき。
- 安全対策・冗長設計・フェイルセーフの**効果を発生確率で定量評価**し、投資対効果を比較したいとき。
- 事故・重大トラブルの**事後解析**で、複数要因の論理的な絡み合いを構造化して再発防止に繋げたいとき。

**使わない / よくある誤用（アンチパターン）**
- **トップ事象を1つに絞らずに始める**——最頻の誤り。FTAは1つのトップ事象専用の木。複数事象を同じ木に混ぜると
  論理が破綻する。事象ごとに別の木を作る。
- **原因が1本道で明らか／軽微なミスに重装備で使う**——単線の深掘りで足りるなら**なぜなぜ分析**、
  幅広い要因列挙なら**特性要因図**で十分。FTAは論理ゲートと確率計算のコストに見合う重大事象にだけ使う。
- **ゲートを付けずに枝を並べるだけ**——AND/ORを明示しない木はただのツリー図で、最小カットセットも確率も出せない。
  各分岐が「すべて必要(AND)」か「どれか1つで十分(OR)」かを必ず判定する。
- **確率を根拠なく置く**——基本事象の故障率が当て推量だと定量結果は幻。データ（実績故障率・信頼性データベース）の
  裏づけが無い数値は「推計・要検証」と明示し、確率は感度分析で幅で見る。
- **共通原因故障を見落とす**——独立を前提にAND確率を掛け算すると、1つの原因（停電・浸水・設計欠陥）が複数系統を
  同時に潰す**共通原因故障**を過小評価する。冗長化してもここが穴になる。別途チェックする。
- **木の完全性を過信する**——想定しなかった故障経路はツリーに現れない。網羅は保証されない（→前提と限界）。
- **静的な一枚で固定する**——摩耗・経年・事象の順序（どちらが先に壊れたか）は古典FTAでは表現しない。

## 前提と限界

- **前提**: (1)分析対象の**トップ事象を1つに具体的に定義**できること（「事故」でなく「◯◯装置が△△の状態で停止」）。
  (2)システムの構造・機能・故障モードを理解していること（設計図・工程・関係者の知見）。(3)定量評価するなら
  各基本事象の**発生確率/故障率のデータ**が取れること。無ければ定性（最小カットセット）だけでも価値がある。
- **限界（批判を踏まえて）**:
  - **静的・二値前提**——各事象は「故障／正常」の2値で、時間変化・摩耗・**事象の起きる順序**を表現しない。
    順序や時間依存を扱うには**動的故障木（Dynamic Fault Tree）**への拡張が要る。
  - **共通原因故障（common cause failure）に弱い**——独立を仮定して確率を掛けるため、単一の根本原因が複数系統を
    同時に無効化するケースを取りこぼす。冗長設計の落とし穴。
  - **主観・専門家依存**——故障モードの洗い出しとツリーの組み方がアナリストの経験・視点に依存し、**網羅性は保証されない**。
    想定外の経路は木に現れない（完全性の非保証）。
  - **構築コストが高い**——大規模システムでは木が巨大化し、作成・保守・確率データ収集に労力がかかる。
  - **原因の列挙ではなく論理分解が本質**——「要因を広く出す」目的には向かない。そこは特性要因図やブレストの領分。
- これらは、**部品起点の網羅はFMEA（ボトムアップ）で、要因の幅出しは特性要因図で、単線の深掘りはなぜなぜ分析で、
  対策の追跡はPDCA/QCストーリーで**補える（→相性）。

## 進め方（手順）

命令形で示す。各ステップに「なぜ」を添える。**AND/ORの判定と、確率の裏づけ**が肝。

1. **トップ事象を1つ、具体的に定義する。** 「何が・どの状態で・どこで」起きる望ましくない事象かを一文で固定する
   （例「制御弁が閉じず薬液が過剰供給される」）。境界（対象システムの範囲・成功/失敗の定義）も決める。
   なぜ: FTAは1事象専用の木。頂点が曖昧だと以降の分解がすべて発散する。粒度が高すぎても低すぎても使えない。
2. **システムを理解する。** 構成要素・機能・信号や物の流れ・既知の故障モードを、設計図・工程・現場知見から把握する。
   なぜ: 論理を正しく引くには対象の仕組みの理解が不可欠。理解の穴がそのまま木の穴になる。
3. **トップ事象の直下の原因を一段だけ洗い、ゲートで結ぶ。** 「この事象が起きるには何が必要か」を一段分解し、
   **すべて揃って初めて起きるならAND、どれか1つで起きるならOR**で結ぶ。
   なぜ: 一段ずつ論理関係を確定するのがFTAの心臓部。ここでAND/ORを曖昧にすると最小カットセットも確率も狂う。
4. **各中間事象を、基本事象に達するまで同様に分解する。** これ以上分解しない末端（基本事象＝円）、情報不足で
   止める点（非展開事象＝菱形）まで一段ずつ下ろす。同じ基本事象が複数箇所に出るなら同一ラベルを付ける。
   なぜ: 末端まで下ろして初めて弱点の最小単位が見える。共有事象を同一視しないと確率計算を誤る。
5. **定性評価: 最小カットセットを導く。** トップから下へ、**ORゲートは行を分岐（増やす）、ANDゲートは同じ組に併記（横に広げる）**
   して展開し、冗長な組を吸収律で消して最小化する。**要素1個のMCS＝単一障害点**をまず洗い出す。
   なぜ: 最小カットセットはシステムの弱点の最小単位。単一障害点は一箇所の対策で最大の効果が出る最優先ポイント。
6. **定量評価: 発生確率を計算する（データがあれば）。** 基本事象に故障率/発生確率を与え、
   **ANDは掛け算（P=Pa×Pb…）、ORは足し算の近似（P≈Pa+Pb…、希少事象近似）**でトップまで積み上げる。
   なぜ: 確率は「どのMCSが効くか」を定量比較させ、対策の優先順位と冗長化の効果を金額・リスクで語れるようにする。
7. **弱点を特定し、対策に変換する。** 単一障害点・確率寄与の大きいMCS・共通原因故障の穴を挙げ、
   **原因除去／冗長化（ANDに変える）／検知・監視／フェイルセーフ**のどれで潰すかを決める。対策後の確率も試算する。
   なぜ: FTAはゴールでなく起点。ORをANDに変える（多重化する）と確率が桁で下がる——構造を「変えられる対象」に落とす。
8. **前提・共通原因・想定外経路を検算する。** 確率の出所、独立の仮定が崩れないか（共通原因）、木に載っていない
   故障経路が無いかを問い直し、検証すべき仮説と次の一手を1〜3個決める。
   なぜ: 掛け算の独立前提と木の完全性はFTA最大の盲点。機械的な確率を鵜呑みにせず揺さぶってから確定する。

## 壁打ち質問リスト

各要素を事実で埋めるために、利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す。

1. 防ぎたい**望ましくない事象（トップ事象）は具体的に何**ですか？「何が・どの状態で・どこで」起きる事象か、
   一文で言い切れますか？（複数あるなら、まず1つに絞れますか）
2. その事象が起きると**どれだけの損害・危険**がありますか？（FTAの重装備に見合う重大事象かの確認）
3. トップ事象が起きるには、**すべての条件が揃う必要（AND）**がありますか、それとも**どれか1つで起きます（OR）**か？
   直下の原因を挙げると何がありますか？
4. 各原因は**さらに分解できます**か？どこまで下ろすと「これ以上は分けない末端（基本事象）」に届きますか？
   情報不足で止まる点（非展開事象）はどこですか？
5. **同じ原因が複数の枝に共通して効いていません**か？（停電・浸水・共通部品・共通の設計/運用ミスなど＝共通原因故障）
6. 各基本事象の**発生確率・故障率のデータ**はありますか？（実績・信頼性データベース・試験。無ければどれが推計ですか）
7. **単一障害点（ひとつ壊れると全部止まる箇所）**に心当たりはありますか？そこは冗長化されていますか？
8. すでに入っている**安全対策・冗長化・監視**は何ですか？それは木のどのゲートを「OR→AND」に変えていますか？
9. どの**時間軸・使用条件**で見ますか？（経年・摩耗・起動時/連続運転時で故障率が変わりませんか）

## 出力フォーマット

ALWAYS この型で出力する（木の論理構造 → 最小カットセット/確率 → 対策）。単なる原因列挙で止めない。

```
【FTA（故障の木）】トップ事象: <何が・どの状態で・どこで> ／ 対象範囲: <システム境界> ／ 目的: <特定したいこと>

  トップ事象
   └─[AND/OR]
       ├─ 中間事象A ─[AND/OR]─ ├─ 基本事象a1 (P=<確率/推計>)
       │                        └─ 基本事象a2 (P=<…>)
       └─ 中間事象B ─[AND/OR]─ ├─ 基本事象b1 (P=<…>)
                                └─ 非展開事象b2 (情報不足)
  ※各ゲートは AND(全て揃って発生) / OR(いずれかで発生) を明記する

【最小カットセット（定性＝弱点）】
  単一障害点(要素1個): - {a1} … ← 最優先。一箇所の対策で最大効果
  複合(要素2個以上):   - {b1, b2} …（ANDで重なって初めて起きる組）

【発生確率（定量＝データがあれば）】
  トップ事象の推定確率: <値>（AND=積, OR=和の近似で算出）／ 最大寄与のMCS: <どの組が効くか>

【対策への変換】
  除去:   <原因そのものを無くす>
  冗長化: <OR→ANDに変える＝多重化する箇所> → 対策後の確率: <試算>
  検知:   <監視・警報で兆候を捉える>
  ※共通原因故障（1原因で複数系統が同時故障）の穴も明記

【次の一手】<検証すべき仮説・意思決定・対策を1〜3個。単一障害点の優先処置>
【未確認の前提】<確率データの出所・独立の仮定・木に載っていない故障経路——裏取りが要る点>
```

## 具体例（ワークスルー）

対象を一般化した例（架空の数値・企業名は用いない）。ある**Webサービスが「ユーザーがログインできない」**という
重大事象を、FTAで論理分解する場面。

- **手順①トップ事象**: 「正規ユーザーがログイン処理を完了できない」。境界＝認証機能に限定し、成功=トークン発行までと定義。
- **手順②システム理解**: 構成は「認証API」「ユーザーDB」「セッション基盤」「ネットワーク経路」。各々の故障モードを把握。
- **手順③直下の分解（OR）**: ログイン不可は「認証APIが応答しない」**または**「認証は通るがセッションを張れない」**または**
  「ネットワークで到達できない」——**どれか1つで起きる＝ORゲート**。
- **手順④さらに分解**: 「認証APIが応答しない」を分解＝「APIサーバ全滅」**かつ**「フェイルオーバー先も不可」＝**ANDゲート**
  （冗長化されているため両方揃って初めて起きる）。末端＝「主系ダウン(基本事象)」「予備系ダウン(基本事象)」。
  「ユーザーDB照会不可」は主系・レプリカのANDに分解。
- **手順⑤最小カットセット**: 展開すると——**単一障害点**として「ネットワーク単一経路の切断{経路故障}」（要素1個）が判明。
  一方 API は{主系ダウン, 予備系ダウン}の2要素MCS（冗長が効いている）。→ネットワーク経路が最大の弱点。
- **手順⑥確率**: 各基本事象に実績故障率を与え、APIのANDは積（小さい）、全体のトップはORの和で近似。
  最大寄与は単一経路の{経路故障}と判明。
- **手順⑦対策変換**: 単一障害点の経路を**冗長化（OR→AND化＝2経路の同時故障で初めて不通）**、DBは監視で予兆検知、
  対策後のトップ確率を再試算して桁で低減することを確認。
- **手順⑧検算**: 「主系と予備系が**同じ電源/同じデータセンター**なら共通原因故障で同時に落ちる」＝独立前提が崩れる点を明示。
- **次の一手**: ネットワーク経路の冗長化を最優先。主系/予備系の電源・拠点の分離を検証（共通原因の排除）。
- **未確認の前提**: 各基本事象の故障率の出所、冗長系の独立性、想定外の故障経路（例: 設定ミスの波及）——実データで裏取りが要る。

## 相性（組み合わせると効く）

- `fishbone`（特性要因図）: FTAが論理ゲートで**構造化**する前段として、要因を4M等で**幅広く列挙**する。網羅の抜けを減らす相棒。
- `five-whys`（なぜなぜ分析）: FTAで特定した基本事象や単一障害点の**真因を単線で深掘り**し、恒久対策の当てどころを外さない。
- `logic-tree`（ロジックツリー）: 汎用の課題分解。FTAは「故障の因果をAND/ORゲートと確率で定量化した特殊形」と捉えると、
  一般の分解（logic-tree）との違い＝論理演算と最小カットセットが明確になる。
- `qc-story`: 品質問題解決のプロセスの「原因分析」工程にFTAを差し込み、対策・標準化・歯止めまで繋ぐ器にする。
- `pdca`: FTAで出した対策と監視指標（トリガー）をPDCAに載せ、実行と効果検証（対策後の確率低減）を追跡する。
- 揺さぶり枠として `premortem`（プレモータム）: 「もう大事故が起きた」と仮定して失敗経路を先に想像し、FTAの木に
  載っていない想定外経路・共通原因故障を炙り出す。FTAの完全性の非保証を補う。
- **対をなす手法（本文で言及、スキル未登録）**: **FMEA**（部品の故障モードをボトムアップで帰納的に積み上げる）は
  FTA（トップ事象からトップダウンで演繹）と方向が逆。航空宇宙では両方実施が通例。**イベントツリー**は起因事象から
  前向きに波及を追う（FTAは後ろ向き）——併用で因果を双方向から挟む。
