# リーンスタートアップ / MVP

## 概要

リーンスタートアップは、**極度の不確実性**の下で新事業・新製品を立ち上げるための方法論。核心は
「作り込んでから売れるか確かめる」順序を逆転させ、**作る前に最小の実験で仮説を検証**し、ムダ
（時間・資金・労力）を削ること。進捗の単位を売上や機能数でなく **検証された学び（validated learning）**
に置く。

中心にあるのが **Build-Measure-Learn（構築-計測-学習）ループ**——アイデアを最小の製品にして出し、
顧客の反応を実データで測り、学んで **Pivot（方向転換）or Persevere（継続）** を決める。この最小の
製品が **MVP（Minimum Viable Product / 実用最小限の製品）** で、Ries の定義は
「最小の労力で、顧客に関する**検証された学びを最大限**得られる、新製品のバージョン」。

| 概念 | 意味 | 実務での問い |
|---|---|---|
| **検証された学び** | 進捗の単位。売上/機能でなく「何が真と分かったか」 | 今回のMVPで何を学べたか？ |
| **MVP** | 学びを得るための最小の実験（完成品でなく実験） | これ以上削れないか？ |
| **革新会計** | 学習進捗を測るスタートアップ固有の指標運用 | どの数字で合否を判断するか？ |
| **ピボット** | 製品/戦略/成長エンジンの根本仮説を変える構造的な軌道修正 | 変えるべきは何か、何を残すか？ |

- **核となる考え方**: 新規事業の最大のリスクは「作れないこと」より「作っても誰も欲しがらないこと」。
  だから最初に潰すべきは**技術リスクでなく市場/需要リスク**。最重要の前提を、最も安く速い実験で試す。
- **出自（諸説あり・要確認）**: 「MVP」という用語は **Frank Robinson（SyncDev社）が2001年に考案**したと
  され、その定義は「採用・満足・売上を生む程度に大きく、肥大化しない程度に小さい、ちょうど良い**製品**」と
  経済性重視で*実際に機能する製品*寄り。これを **Steve Blank の顧客開発（Customer Development, 2005年
  『The Four Steps to the Epiphany』）** の系譜の上で、**Eric Ries が2008年に「lean startup」として提唱・
  2011年『The Lean Startup』で普及**させた。Ries の MVP は Robinson と異なり *実験（experiment）* 寄りに
  再定義されている。「lean（リーン）」の語源はトヨタ生産方式（ムダ排除の思想）。**用語の命名者と普及者は
  別**——「MVPはRiesの発案」は不正確（→出典・要確認）。

## いつ使う / 使わない

**使う（適する状況）**
- 新規事業・新製品・新機能で、**顧客・課題・解決策・価格に大きな不確実性**があり「そもそも需要があるか」
  自体が未知のとき。
- **作り込む前に**、需要・価値・意思（買うか/使うか/払うか）を安く速く確かめたいとき。
- PoC/実証実験・βテスト・事前予約・クラウドファンディング等、**小さく試す設計**を組みたいとき。
- 「作ったのに売れない」の後、**何が外れたのかを検証**し、継続かピボットかを判断したいとき。
- Web/アプリ/サービスなど、**低コストで反復・計測できる**領域。

**使わない / よくある誤用（アンチパターン）**
- **MVP＝「安く雑に作った不完全な製品」と誤解する**——最頻の誤用。MVPは品質を落とした製品ではなく
  *学びを得る実験*。低品質を出荷してブランドを毀損したら本末転倒（Jeff Gothelf らは "Stop saying MVP" と
  用語の乱用を批判）。「何を学ぶための実験か」を先に決める。
- **虚栄の指標（vanity metrics）で判断する**——累計DL数・PV・総登録数など「良く見えるが打ち手に繋がらない」
  数字で継続を誤判断する。コホート別の継続率・転換率など**実用的指標（actionable metrics）**を見る。
- **早すぎるピボット（premature pivot）**——データでなく飽き・焦りで方向転換し、粘れば伸びた芽を摘む。
  ピボットは事前に決めた合否ラインを割ったときに、**データを根拠に**行う。
- **合否ラインを事後に決める**——出た数字を見てから「成功」と解釈する確証バイアス。閾値は実験前に固定する。
- **全機能を作ってからMVPと呼ぶ**——「最小」でない。最重要リスク仮説1つに絞って削る。
- **適さない領域**: 要求・正解が既知で実行あるのみの局面。規制・安全・物理制約で小さく出せない領域
  （医療機器・航空・原子力・重厚長大なハード等）。試作/検証コストが便益を上回る場合。実験結果を解釈する
  経験がチームに無い場合。長期ビジョンの作り込みが本質の領域では反復偏重が構想を痩せさせ得る。

## 前提と限界

- **前提**: 検証対象の事業アイデアが1つに定まり、そこに**明文化できる仮説**があること。仮説が曖昧だと
  MVPも合否ラインも設計できない。安く速く試せる手段（LP・手作業・試作）にアクセスできること。
- **限界（批判を踏まえて）**:
  - **漸進的改善に偏りがち**——反復最適化はローカル最適に留まり、破壊的イノベーションが出にくいとの批判
    （学術系の Felin/Gambardella/Stern/Zenger らは「製造原理を起業に当てると漸進的成果に留まる」と指摘）。
  - **万能ではない**——Ben Horowitz は「lean（痩せ我慢）偏重は競争力を犠牲にする」と批判。ある論考は
    (1)プロトタイピング費用が極端に高い領域、(2)検証コストが便益を超える場合、(3)実験結果を解釈する経験が
    無いチーム、の3条件では適さないとした。
  - **早すぎる撤退のリスク**——Pinterest 共同創業者 Ben Silbermann は「作っている時に The Lean Startup を
    読まなくてよかった、読んでいたら早々に諦めていた」と述べたとされる（要確認）。強いビジョンが要る事業では
    検証至上主義が足を引っ張り得る。
  - **「検証された学び」の落とし穴**——実験設計が悪いと、誤った結論を「検証済み」と誤認する。仮説・指標・
    閾値・母集団の質が全て。
- これらは、**価値仮説をVPC/JTBDで鋭くする / 事業全体をリーンキャンバスで俯瞰する / 検証の失敗要因を
  premortem で先回りする / 継続判断の確証バイアスを devils-advocate で疑う**ことで補える（→相性）。

## 進め方（手順）

命令形で示す。各ステップの「なぜ」を添える。

1. **一足飛びの前提（leap-of-faith assumptions）を洗い出す。** 「これが偽なら事業が死ぬ」前提を、
   **価値仮説**（顧客はこの課題を、この解決策で、対価を払うほど解きたい）と**成長仮説**（どう広がるか）に
   分けて列挙する。
   なぜ: 検証すべきは全部でなく「壊れたら致命的な少数」。ここを外すと安全な枝葉ばかり試して核心に届かない。
2. **最重要のリスク仮説を1つ選ぶ。** 「不確実性が高く、かつ外れたら被害が最大」の前提を先に置く
   （多くは技術リスクでなく需要/価値リスク）。
   なぜ: 一度に1つしか厳密には検証できない。優先順位を誤ると、作り込んだ後に前提崩壊が起きる。
3. **合否ライン（指標と閾値）を実験前に決める。** 「何人中何人が登録/購入/継続したら仮説は支持」と、
   **actionable metric** で先に固定する。虚栄の指標は使わない。
   なぜ: 事後に基準を作ると必ず「成功」に解釈できてしまう（確証バイアス）。閾値は動かさない前提で置く。
4. **その仮説だけを検証する最小のMVPを設計する。** 型を選ぶ（下表）。**それ以上削れないか**を問う。
   なぜ: 学びに寄与しない機能は全てムダ。目的は製品でなく学び。作らずに済むなら作らない。
   | MVPの型 | 何を検証 | 例 |
   |---|---|---|
   | ランディングページ/スモークテスト | 需要・関心（事前登録/予約） | 紹介ページ＋広告で登録率を見る |
   | フェイクドア | 既存製品での新機能需要 | 未実装ボタンのクリック率 |
   | コンシェルジュ | 価値（手作業で提供、顧客は手動と承知） | 少数顧客に人力でサービス |
   | オズの魔法使い | 体験（表は自動に見せ裏は手作業） | 完成品に見せて人が処理 |
   | 単一機能製品 | 中核機能の価値 | 主要1機能だけ実装 |
   | 先に売る | 支払い意思 | 予約販売/クラウドファンディング |
5. **Build → Measure → Learn を回す。** MVPを出し、**行動ベースの実データ**で測る（言葉でなく行動）。
   コホート分析・A/Bで actionable metric を見る。
   なぜ: アンケートの「欲しい」と実際の登録/購入は別。意見でなく行動で測ると仮説の真偽が出る。
6. **Pivot（方向転換）or Persevere（継続）を判断する。** 合否ラインを超えたら継続・深掘り、割ったら
   ピボットを検討。ピボットは種類を選ぶ（ズームイン/アウト、顧客セグメント、顧客ニーズ、プラットフォーム、
   チャネル、技術、成長エンジン 等）。
   なぜ: 判断を先延ばすとゾンビ化する。ただし飽き・焦りでなく**データを根拠に**決める（早すぎるピボットを避ける）。
7. **次の実験に繋ぐ。** 学びを言語化し（「Xは真/偽と分かった」）、次に最重要となった前提を選んで手順2へ戻る。
   なぜ: リーンは1回で終わらない。ループを速く回すほど、限られた資源で学びが積み上がる。

## 壁打ち質問リスト

各要素を事実で埋めるために、利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す。

1. この事業/製品で**「これが偽なら終わる」という前提**は何ですか？（顧客は誰か／その課題は本当に痛いか／
   この解決策で解けるか／対価を払うか——どれが一番あやしいですか？）
2. その前提のうち、**今いちばん不確実で、外れたら被害が大きいもの**はどれですか？（＝最初に検証すべき1つ）
3. その仮説が**「支持された」と言える具体的な数字と閾値**は何ですか？（例: 訪問者の何％が登録/購入したら合格、を
   実験前に決められますか？）
4. すでに追っている指標のうち、**見栄えは良いが判断に使えない数字（虚栄の指標）**はどれで、代わりに見るべき
   **行動ベースの指標**は何ですか？
5. その仮説を検証するのに、**作らずに済ませる方法**はありますか？（LP・手作業・予約販売など、どの型が最小ですか？）
6. 検証の結果、**合格なら次に何を確かめ、不合格ならどうピボットする**か——分岐を先に決めていますか？
7. この検証にかけられる**時間・予算・人の上限**はどれくらいですか？（実験の規模と速さを規定する）
8. 顧客の「欲しい」という**言葉**でなく、登録・支払い・再訪などの**行動**で測れる設計になっていますか？

## 出力フォーマット

ALWAYS この2段構えで出力する（実験設計 → 判断）。各実験は1枚のカードにまとめる。

```
【検証キャンバス】対象: <事業/製品/機能> ／ このループで確かめたいこと: <一言>
  一足飛びの前提（優先順）:
    価値仮説:  - <誰の・どの課題・どの解決策・対価> …
    成長仮説:  - <どう広がるか> …
  今回の最重要リスク仮説: <1つに絞った検証対象>

【MVP実験設計】
  MVPの型:   <LP/フェイクドア/コンシェルジュ/オズ/単一機能/先に売る>
  作るもの:  <学びに必要な最小限。削った物も明記>
  計測指標:  <actionable metric（行動ベース）> ／ 虚栄の指標として捨てる数字: <…>
  合否ライン: <実験前に固定した閾値。例: 登録率○％以上で支持>
  規模/期間: <母集団・サンプル数・実施期間・予算の上限>

【判断（実験後に記入）】
  結果:      <実データ>
  学び:      <Xは真/偽と分かった＝validated learning>
  Pivot or Persevere: <継続 / ピボット（種類を明記）> ／ 根拠: <データ>
  次の実験:  <次に検証する最重要前提>
【未確認の前提】<まだ検証していない致命的前提（次以降で潰す）>
```

## 具体例（ワークスルー）

対象を一般化した例（架空の数値・企業名は用いない）。**都市部の共働き世帯向けに「作り置き総菜の定期宅配」を
検討する**個人が、開発に踏み切る前に検証する場面。

- **手順①前提の洗い出し**:
  - 価値仮説: 共働き世帯は「平日夕食の準備負担」を痛みに感じ、作り置き宅配に月額を払ってでも解きたい。
  - 成長仮説: 満足した利用者が口コミ/紹介で広げる（バイラル型を想定）。
- **手順②最重要リスク仮説**: 「調理は自分でできる（技術リスク低）」より「**そもそも月額を払ってでも欲しい人が
  いるか（需要/支払い意思）**」が最も不確実で致命的。これを最初に検証する。
- **手順③合否ライン**: 「紹介ページを見た訪問者のうち、事前予約（少額デポジット）まで進む割合が一定水準を
  超えたら、支払い意思あり」と**実験前に**閾値を決める（水準は自分の採算前提から逆算）。
- **手順④最小のMVP**: 厨房も物流も作らない。**ランディングページ＋先に売る型**——メニュー例と価格を提示し、
  「事前予約（返金可の少額デポジット）」ボタンを置く。まだ商品は無い。
- **手順⑤Build-Measure-Learn**: 小さな広告で対象地域の訪問を集め、**予約という行動**で測る（「興味ある」の
  クリックでなく、デポジット完了を合格条件にする＝行動ベース）。
- **手順⑥判断**: 予約率が閾値を超えれば継続（次はオペレーションの実現性を検証）。届かなければ、
  「**顧客セグメントのピボット**（共働き世帯→高齢単身世帯へ）」か「**顧客ニーズのピボット**（作り置き→
  下ごしらえキット）」を、予約フォームで得た反応データを根拠に検討する。
- **手順⑦次の実験**: 需要が支持されたら、次の最重要前提「1食あたり原価と配送で採算が取れるか」を
  コンシェルジュMVP（少数世帯に手作業で届ける）で検証する。
- **未確認の前提**: 継続率（初月は予約しても2ヶ月目に続くか）、配送コスト、食品衛生・許認可——ここは
  推測のまま進めず、後続ループで実データを取る。

## 相性（組み合わせると効く）

- `lean-canvas`: 事業全体を1枚に整理し、**検証すべき前提（特に課題・顧客・独自価値）**を洗い出す前工程。
  リーンスタートアップの入力を作る。
- `value-proposition-canvas`: 価値仮説（顧客の課題・利得と提供価値の対応）を精緻化し、MVPで何を試すかを鋭くする。
- `jtbd`: 顧客の「片付けたい用事」を捉え、検証すべき**課題仮説**を本質から立て直す（誤った課題を検証する空振りを防ぐ）。
- `payoff-matrix`: 複数の検証施策やピボット候補を「効果×実現性」で並べ、次に回す実験の優先順位をつける。
- 揺さぶり枠として `premortem`（「このMVP検証は失敗した」と仮定し、実験設計の穴・誤った合否ラインを先回り）や
  `devils-advocate`（「継続」判断に対し反対役を立て、虚栄の指標や確証バイアスを暴く）を添えると、
  早すぎるピボット/粘りすぎの両方向の誤判断を減らせる。
