# ECRS（改善の4原則）

## 概要

ECRS（日本では「イクルス」とも）は、既存の業務・工程・作業を改善するときの **視点と検討順序** を
示した、IE（インダストリアルエンジニアリング）由来の改善原則。4つの頭文字を、
**効果が大きい順に E→C→R→S** で当てていく。

| 順 | 記号 | 意味 | 問い（合言葉） |
|---|---|---|---|
| 1 | **E** Eliminate（排除） | その作業・工程・動作を無くす | 「そもそも要るのか？無くせないか？」 |
| 2 | **C** Combine（結合／分離） | 複数をまとめる（時に分ける） | 「一緒に／同時にできないか？」 |
| 3 | **R** Rearrange（交換・再配置） | 順序・場所・担当を入れ替える／代替する | 「順番・場所・人を変えられないか？」 |
| 4 | **S** Simplify（簡素化） | 残った作業をより簡単にする | 「もっと単純・楽にできないか？」 |

- **核となる考え方**: **「引き算（減らす）の改善を、足し算（作り込む・自動化する）の改善より先に」**。
  作業を1つ無くせば（E）、その作業に付随する準備・移動・記録・検査までが連鎖的に消える。
  だから最も効果が高いEから問い、C→R→Sと進むほど1件あたりの効果は小さくなる——これが順序の意味。
  最後のSで初めてツール導入・自動化を検討する（ムダを残したまま高速化しないため）。
- **適用の粒度は自在**: 工程レベル・作業レベル・動作レベルのどこにでも当てられる（階層的に使える）。
- **出自（諸説あり・単一断定は避ける）**: ECRSは IE の共有知で、考案者を1人に確定しにくい。
  よく引かれる原典は **Ralph M. Barnes** の教科書 *Motion and Time Study*（作業方法の設計の章で
  「不要な作業の排除／作業や要素の結合／作業順序の変更／必要作業の簡素化」を提示）。
  より広くは、IEの **メソッドスタディ（作業研究）の疑問法** に同じ発想が組み込まれており、
  ILO『Introduction to Work Study』が疑問法を体系化している。**起源は複数系譜の合流として扱う**
  （書名の版・年、単一帰属は→出典・要確認項目参照）。

## いつ使う / 使わない

**使う（適する状況）**
- 既存の**定型業務・製造工程・事務プロセス**のムダ取り、**工数削減・リードタイム短縮・残業削減**。
- 現場の**カイゼン**、業務標準・手順の見直し、二重入力・重複チェック・不要会議の整理。
- **DX・システム化の前段**で、まず業務そのものを棚卸し・スリム化したいとき
  （無駄な業務を自動化して固定化しないために、自動化・システム化する前にECRSを通す）。
- バリューストリームマッピングやなぜなぜ分析で**洗い出したムダ・要因を、具体的な打ち手に変換**したいとき。

**使わない / よくある誤用（アンチパターン）**
- **順序を無視していきなりS（簡素化）へ飛ぶ**——最頻の失敗。特に「RPA・システム導入で自動化」から入ると、
  本来**無くせる作業（E）を高速に回すだけ**の"ムダの自動化"になる。必ず「無くせないか」から問う。
- **「排除＝リストラ・手抜き」と誤解**——目的は付加価値を生まない作業の除去。価値ある作業や必要な検査まで
  削るのは誤り。まず「何が付加価値か」を合意してから排除に入る。抵抗を生みやすいので目的の共有が要る。
- **結合(C)を万能視する**——まとめれば良いとは限らない。属性の違う業務は**分離した方が効率的**な場合もある
  （Cは結合と分離の両面）。担当の兼務化で逆に品質が落ちることもある。
- **自部署だけで完結させる**——多くの業務は部門をまたぐ。関係部署が変わらないと局所最適で終わる。
- **目的・指標なしで手段が自己目的化**——「無くす/まとめる」こと自体が目的化し、現場が疲弊する。
- 真因が未特定の品質問題の**原因究明そのもの**、ゼロからの**新規アイデア発想**、戦略・市場分析には不向き。
  ECRSは「既にある工程を改善する打ち手の枠」。前工程は別フレームで回してから渡す（→相性）。

## 前提と限界

- **前提**: 対象の作業・工程が**可視化・分解できる**こと（工程分析・動作分析・業務棚卸しが済んでいる、
  または壁打ちで引き出せる）。繰り返し性のある定型業務であること。改善の**目的と効果指標**が1つ定まっていること。
- **限界**:
  - **改善"案"を出す発想の枠であって、真因分析や制約特定そのものではない**。「なぜこの作業があるのか」
    「どこがボトルネックか」は、なぜなぜ分析・特性要因図・TOC・VSMが担う。ECRSはその後段の変換器。
  - **「E→C→R→Sは改善効果の降順」は実務の経験則**であり、定量的に証明された法則ではない。目安として使い、
    個別ケースでは効果とコストを実測して優先順位を決める（順序は"検討の順"であって"実施必須の順"ではない）。
  - **静的**——一度スリム化しても業務は再び肥大化する。定期的に回す前提（PDCAに組み込む）。
  - **局所最適の罠**——一工程を最適化すると前後にしわ寄せが出ることがある。全体最適はVSM/TOCで俯瞰する。
- これらは、**前段になぜなぜ/VSMを置く・優先順位づけにペイオフマトリクスを併用する・PDCAで定着させる**
  ことで補える（→相性）。

## 進め方（手順）

命令形で示す。各ステップの「なぜ」を添える。

1. **対象と目的・指標を1つに固定する。** 「どの業務／工程を、何のために、どの指標（工数・時間・件数・
   コスト・ミス率）で改善するか」を明文化する。
   なぜ: 目的がないと「無くす/まとめる」が自己目的化し、現場を疲弊させる最頻の失敗に直結する。
2. **現状を可視化・分解する。** 対象の作業・工程を書き出し、5W1H（What/Where/When/Who/How＋なぜWhy）で
   事実を押さえる。付加価値作業と非付加価値作業（ムダ・待ち・運搬・手直し等）を仕分ける。
   なぜ: 分解しないと排除・結合の対象が見えない。「なぜこの作業があるのか」を各要素に当てておく。
3. **E（排除）を最初に問う。** 各作業・工程に「無くしても目的を損なわないか」をぶつける。誰も見ない資料、
   重複確認、不要な会議・承認、過剰な検査、無駄な移動・待ちを探す。
   なぜ: 排除は連鎖効果が最大（付随作業も一緒に消える）。ここを飛ばすと後工程で無駄を磨き込んでしまう。
4. **C（結合／分離）を問う。** 無くせない作業について「まとめる／同時化できないか」。工具・治具・帳票・
   機能・工程・担当の統合を検討する。**逆に、分けた方が速い・正確な場合は分離も候補にする。**
   なぜ: まとめると段取り・運搬・持ち替えが減る。ただし結合が常に善ではない点に注意（分離の視点も持つ）。
5. **R（交換・再配置）を問う。** 残った作業の「順序・場所・担当・道具を入れ替える／代替できないか」。
   人の動線に合わせた工程の並べ替え、取り出し位置の変更、担当替え、前後工程の入替え。
   なぜ: モノや人の動きのムダは順序と配置で大きく変わる。設備投資なしで効く打ち手が多い。
6. **S（簡素化）を問う。** ここで初めて「残った必要作業をより簡単・単純にできないか」。治具・テンプレート・
   視覚化・ワンタッチ化・入力自動化・システム/RPA導入を検討する。
   なぜ: E〜Rで筋肉質にした後の作業だけを自動化・作り込みする。順序を守ることで"ムダの自動化"を避ける。
7. **対策案を評価し、優先順位づけして実施する。** 出た案を **効果 × 実現の容易性 × コスト** の3点で採点し、
   効果が高く実現しやすいものから着手する。実施後は指標で効果測定し、標準化して定着させる。
   なぜ: 案は出しただけでは価値がない。効果・実現性で絞り、測って、標準に落として初めて改善が完了する。

## 壁打ち質問リスト

各要素を事実で埋めるために、利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す。

1. 改善したいのは**どの業務・工程**ですか？そして**何の指標**（作業時間・工数・リードタイム・件数・
   コスト・ミス率など）を、どれくらい良くしたいですか？（目的と物差しを1つに）
2. その業務の**手順を、始まりから終わりまで**順に挙げてください。各ステップに誰が・どこで・どれくらいの
   時間がかかっていますか？（5W1Hで現状を可視化）
3. 各ステップについて、**「これは何のためにあるのか」「無くしたら誰が困るのか」**を説明できますか？
   説明に詰まる作業はありませんか？（E＝排除の候補あぶり出し）
4. **重複・二度手間・待ち時間・差し戻し・不要な承認や会議**になっている箇所はどこですか？
   （非付加価値作業の特定）
5. 別々にやっている作業で**まとめられそう／同時にできそう**なものはありますか？逆に、1人・1工程に
   詰め込みすぎて**分けた方が速くなりそう**なものはありますか？（C＝結合と分離）
6. 作業の**順序・場所・担当・使う道具**を変えると楽になりそうな箇所はありますか？人やモノの動線に
   ムダな往復はありませんか？（R＝交換・再配置）
7. この改善は**自部署だけで完結**しますか？変更に**関係部署の合意**が要る箇所はどこですか？
   （部門横断の制約を先に把握）
8. すでに「自動化・システム化しよう」と考えている作業はありますか？——**それは無くせない／まとめられない
   作業だと確認済み**ですか？（S・自動化に飛ぶ前のEC確認）

## 出力フォーマット

ALWAYS この型で出力する（現状→ECRS別の改善案→優先順位→次の一手）。命令形で埋める。

```
【対象・目的】業務/工程: <対象> ／ 目的・指標: <何をどれだけ改善するか>
【現状の把握】主なステップ: <始点→…→終点> ／ 特定したムダ: <重複・待ち・運搬・手直し等>

【ECRS 改善案】（E→C→R→S の順に、無くす→まとめる→並べ替える→簡単化）
  E 排除:   - <無くす作業・工程＋根拠（なぜ無くせるか）>
  C 結合:   - <まとめる／同時化する案。分離が有効ならそれも>
  R 交換:   - <順序・場所・担当・道具の入替え・代替案>
  S 簡素化: - <残った作業を簡単化・視覚化・自動化する案>

【優先順位】効果 × 実現性 × コスト で採点し、着手順に並べる
  1. <案> — 効果:高/中/低 実現性:高/中/低 コスト:高/中/低 → <着手判断>
  2. …

【次の一手】<最初に着手する改善1〜2件と、測定する指標>
【未確認の前提／部門横断の論点】<事実確認・関係部署合意が要る点（壁打ちで埋める）>
```

## 具体例（ワークスルー）

対象を一般化した例（架空の数値・企業名は用いない）。ある事務部門の「月次の経費精算処理」を効率化する場面。

- **手順①目的**: 「経費精算の担当者の**処理時間**と**差し戻し件数**を減らす」。対象=月次の精算フロー。
- **手順②可視化**: 申請→上長承認→経理の内容確認→紙の領収書と突合→システム入力→再チェック→支払、と分解。
  ムダ候補=承認が形骸化した多段承認、紙とシステムの二重入力、全件目視の再チェック。
- **手順③E 排除**: 「誰も実質判断していない中間承認」を廃止できないか。「支払前の全件再チェック」を、
  一定金額以下は不要にできないか（=そもそも無くす）。
- **手順④C 結合**: 「内容確認」と「領収書突合」を1つの工程にまとめ、担当を1人にして持ち替えを減らす。
- **手順⑤R 交換**: 「システム入力を最後」から「申請者が最初に入力」へ順序と担当を入れ替え、経理は確認に専念。
- **手順⑥S 簡素化**: 残った確認を、金額・費目の入力チェック（自動バリデーション）やテンプレートで簡単化。
  ここで初めてシステム/RPA化を検討する（E〜Rで作業を削った後なので、自動化対象が小さくなっている）。
- **手順⑦優先順位**: 「多段承認の廃止（効果:高／実現性:中・要部門合意／コスト:低）」を先頭に、
  「二重入力の解消（効果:高／実現性:中／コスト:中）」を次に置く。
- **次の一手**: まず承認段数の見直しを関係部署と合意し、処理時間・差し戻し件数で効果測定する。
- **未確認の前提**: 中間承認が本当に不要か（内部統制・監査要件に触れないか）は、**関係部署と要確認**
  （推測で廃止しない）。

## 相性（組み合わせると効く）

- `value-stream-mapping`: 工程全体のムダ（待ち・在庫・運搬）を俯瞰で可視化し、**ECRSを当てる対象を特定**する
  前工程。局所最適を避け全体最適の視点を与える。
- `five-whys`: 「なぜこの作業があるのか／なぜこのムダが起きるのか」を掘り、**排除(E)の根拠と真因**を固める。
- `fishbone`: ムダ・不具合の要因を体系的に洗い出し、ECRSで潰す打ち手の抜け漏れを防ぐ。
- `lean`: 7つのムダ（作りすぎ・待ち・運搬・加工・在庫・動作・手直し）の思想でECRSの着眼点を広げる同系統の上位思想。
- `payoff-matrix`: ECRSで出た改善案を **効果×実現性** で採点し、着手順を決める（手順⑦の道具）。
- `5s`: 整理・整頓で現場を整え、ECRS（特に排除・再配置）の効果を出しやすい土台を作る補完関係。
- `pdca`: ECRSの改善を一度で終わらせず、計画→実行→評価→改善の**循環に組み込み定着**させる。
- 揺さぶり枠として `reverse-assumption`（「この作業は必要」という前提を反転し排除(E)を強制的に発想）や
  `premortem`（改善が現場で頓挫する失敗要因を先読み）を添えると、排除の踏み込みと定着度が増す。
