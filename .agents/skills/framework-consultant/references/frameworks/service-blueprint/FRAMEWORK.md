# サービスブループリント

## 概要

サービスブループリントは、**ひとつのサービス体験**を時間軸に沿って並べ、それを構成する
**顧客行動・従業員行動（見える／見えない）・支援プロセス・物的証拠**を層（レーン）に分けて可視化し、
**顧客が受け取る「体験の約束」と、それを裏で成立させる「オペレーション」を1枚で接続する**フレームワーク。
カスタマージャーニーが顧客から見える表側だけを描くのに対し、ブループリントは**可視線の下（裏側）まで**描き、
「体験のどこが、裏のどの工程・誰の担当・どのシステムに支えられているか（いないか）」を明らかにする。

標準構造（上から5層。各層は横に時間で流れる）:

| レーン | 中身 | 問い |
|---|---|---|
| **物的証拠(Physical Evidence)** | 各ステップで顧客が接する有形物・場・画面・書類・デジタル証拠 | 顧客は何を目にし・触れるか |
| **顧客行動(Customer Actions)** | 顧客が目標達成のために取る行動・選択（**基点となるアンカー行**） | 顧客は何をするか |
| — **相互作用線(Line of Interaction)** — | 顧客と組織が直接接触する境界 | |
| **フロントステージ(Frontstage／Onstage)** | 顧客から**見える**接点従業員・対顧客システムの行動 | 顧客の目の前で誰が何をするか |
| — **可視線(Line of Visibility)** — | 見える／見えないを分ける**Shostack由来の中核線** | |
| **バックステージ(Backstage)** | 顧客に**見えない**が表側を支える接点従業員の行動 | 舞台裏で何が起きるか |
| — **内部相互作用線(Line of Internal Interaction)** — | 接点従業員と、直接顧客に接しない支援部門の境界 | |
| **支援プロセス(Support Processes)** | 決済・在庫・IT・パートナー等、接点を持たない内部活動 | どの仕組み・部門が支えるか |

- **核となる考え方**: サービスは無形で、顧客・従業員・システムがその場で共創する。ゆえに製品のように
  **設計図（blueprint）**を引かないと、表側の約束と裏側の実装がずれる。表と裏を可視線でまたいで一枚にし、
  **体験を工程・役割・システムの言葉に翻訳する**のが本質。
- **2方向の読み方**: **横＝時間・順序**（各行を左→右に読むと体験が進む）。**縦＝依存関係**（ある顧客ステップの
  真下を読むと、その体験を成立させるために裏で何が起きねばならないかが分かる）。この縦の連鎖が表裏の橋渡し。
- **失敗点(fail point)**: 体験が崩れる箇所・弱点・詰まりを図上に印す。表側の不満を、裏側の原因工程まで縦にたどれる。
- **出自（要確認）**: **G. Lynn Shostack** が **HBR「Designing Services That Deliver」(Jan–Feb 1984)** で提唱
  （当時 **Bankers Trust** 上級副社長）。可視線で onstage/backstage を分ける発想を導入。先行して分子モデル
  (Shostack 1982) がある。現代版は **Bitner, Ostrom & Morgan (2008, California Management Review)** が
  5構成要素・失敗点・読み方に整理し、サービスイノベーションの道具として体系化した（→出典/要確認）。

## いつ使う / 使わない

**使う（適する状況）**
- 顧客体験を、**裏側の業務・役割・システムと突き合わせて**直したいとき。表側の不満の**原因工程**を特定したいとき。
- **部門をまたぐサービス設計・改善**で、関係者全員が同じ一枚で全体像を共有し、責任分界を揃えたいとき。
- **新サービスの提供体制（オペレーション）を設計**するとき。約束する体験を、必要な人員・システム・手順に落とす。
- オンボーディング・申込・サポートなどで、**可視線の下の詰まり（fail point・ボトルネック）**を可視化したいとき。
- 既存のカスタマージャーニーで痛点は分かったが、**「では裏側の誰が何を直すか」**に接続したいとき（＝part two）。

**使わない / よくある誤用（アンチパターン）**
- **顧客に見える表側だけ描いて満足する**——それは実質カスタマージャーニー。可視線の**下**（backstage・支援プロセス）を
  埋めないとブループリントの価値（表裏の接続）が出ない。下段こそ本体。
- **1枚に複数シナリオ／複数ペルソナを詰め込む**——最頻の失敗。経路が違えば図が破綻する。**1シナリオ＋1顧客で1枚**、
  分岐は別紙に。まずスコープを1つに絞る。
- **「あるべき姿(should)」で描く**——理想の工程を並べると机上の図になる。**実際どう動いているか(as-is)**を、
  特に**社内の一次データ**（従業員インタビュー・観察）で接地する。
- **単なる業務フロー図で終わる**——顧客行動というアンカー行を軸に据えず、社内工程だけを並べると顧客と切れる。
  常に「この裏工程はどの顧客ステップを支えているか」を縦で結ぶ。
- **図から直接"解"を出そうとする**——ブループリントは可視化の道具で、**それ自体は解決策を示さない**。失敗点の
  真因分析・対策は別途（fishbone/five-whys/FMEA へ）。
- **作って壁に貼って放置**——チャネル・組織・システムが変われば陳腐化する。失敗点に**担当と見直し時期**を付けて運用する。
- 工程の**流動効率（リードタイム・在庫・付加価値比）の定量改善**そのものには不向き（→value-stream-mapping）。

## 前提と限界

- **前提**: (1) 対象の**サービス体験（シナリオ）と顧客（ペルソナ）が1つに定まっている**こと。曖昧だと図が発散する
  （未定なら persona / customer-journey を先に）。(2) **裏側（frontstage/backstage/支援）にアクセスできる**こと——
  従業員・現場・システム担当から実態を聞ける体制。(3) **社内の一次データ**（インタビュー・観察）で as-is を描けること。
- **限界（批判を踏まえて）**:
  - **1シナリオ1枚の制約**——経路・セグメントが複数あれば複数枚要る。1枚に詰めると複雑化して読めない。
  - **静的スナップショット**——一時点の写真で、環境・チャネル・組織変化を捉えない。定期更新前提で使う。
  - **図自体は解を出さない**——"the blueprint per se cannot suggest solutions"。可視化止まり。真因と対策は別工程。
  - **一次データ依存**——as-is を実データで裏取りしないと、理想像を描いた誤った確信になる。
  - **顧客の深い感情・思考は薄い**——表側の感情曲線の解像度は customer-journey に劣る。役割分担で補う。
  - **流動効率は測らない**——時間・在庫・ムダの定量分析は VSM が担う領域。
- これらは、**主語を persona で固め／表側の感情を customer-journey で深め／失敗点の真因を fishbone・five-whys で掘り／
  fail point を fmea で故障モードとして評価し／裏工程の流動効率を value-stream-mapping で定量改善する**ことで補える（→相性）。

## 進め方（手順）

命令形で示す。各ステップに「なぜ」を添える。**顧客行動をアンカーに置き、その真下に裏側を縦に結ぶ**のが肝。
所要は簡易版で2〜4時間のワークショップ。

1. **対象サービスと目的を1つに固定し、部門横断チームを集める。** どの体験を・何のために描くか（体験崩れの原因特定／
   新体制の設計／部門間の責任分界）を決め、frontstage・backstage・支援・システムの当事者を混ぜる。
   なぜ: サービスは複数部門にまたがる。当事者が欠けると裏側が想像で埋まる。目的が曖昧だと図が発散する。
2. **スコープ（1シナリオ＋1顧客）を絞る。** どのペルソナの、どのシナリオ（例: 初回申込〜利用開始）を1枚にするかを確定する。
   なぜ: 経路が違えば図は破綻する。1枚1シナリオが原則。分岐は別紙に切り出す。
3. **社内中心に一次データを集める。** 従業員インタビュー・現場観察・コンテキスト調査で、**実際の(as-is)**動きを収集する。
   顧客側は既存のジャーニー/調査を流用してよい。なぜ: 「あるべき」で描くと机上の図。裏側は特に想像で埋めやすい。
4. **顧客行動（アンカー行）を横に並べる。** 顧客が目標に至るまでの行動・選択を時間順に置く。
   なぜ: 顧客行動が全レーンの基準線。ここがぶれると縦の対応がずれ、業務フロー図に堕ちる。
5. **物的証拠を顧客行動の上に対応づける。** 各ステップで顧客が接する画面・書類・場・デジタル証拠を書く。
   なぜ: 顧客が「何を見て」体験を判断するかを押さえると、印象を左右する接点が分かる。
6. **可視線の上下を埋める——frontstage → backstage → 支援プロセス。** 相互作用線・可視線・内部相互作用線を引き、
   各顧客ステップの真下に、見える従業員行動／見えない従業員行動／支援活動を縦に積む。
   なぜ: 縦の連鎖こそブループリントの価値。表側の約束を、それを成立させる裏側の実装に翻訳する。
7. **矢印で依存を結び、失敗点(fail point)・ボトルネックを印す。** 誰から誰へ・何が渡るかを矢印で示し、
   体験が崩れる箇所・詰まり・弱点を図上でマークする（dot voting 等で優先度づけ）。
   なぜ: 表側の不満を、裏側の原因工程まで縦にたどれる。優先順位がないと全部は直せない。
8. **時間・メトリクス・規則・感情を足して高精細化する。** 所要時間、成功指標、制約となる規則・ポリシー、従業員の
   フラストレーション点を補う。なぜ: 図を「共有物」から「意思決定に使える資料」に引き上げる。
9. **失敗点を対策・担当・見直し時期に落とし、次の一手にする。** 図自体は解を出さない。優先失敗点ごとに、真因分析へ
   渡すか改善策と担当を決め、検証すべき仮説を1〜3個に絞る。なぜ: 可視化はゴールでなく起点。運用に載せて初めて効く。

## 壁打ち質問リスト

各レーンを事実で埋めるために、利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す（想定は推測と明示）。

1. このブループリントで**最終的に決めたい・直したいこと**は何ですか？（体験崩れの原因特定／新体制の設計／部門間の責任分界）
2. 描く**サービス体験（シナリオ）と顧客（ペルソナ）は1つ**に絞れますか？（複数経路なら図を分けます——どれを最初に描きますか）
3. 対象シナリオで、顧客は**どんな段階（行動）**を、どんな順で通りますか？ ゴールは何ですか？（＝アンカー行）
4. 各ステップで顧客が**目にする・触れる物的証拠**（画面・書類・店舗・メール・アプリ）は何ですか？
5. 顧客の**目の前で**対応する従業員・システム（frontstage）は誰／何ですか？ その裏で**見えないところ**（backstage）では
   誰が何をしていますか？
6. さらにその奥で、**直接顧客に接しない支援部門・システム・パートナー**（決済・在庫・IT等）はどう関わりますか？
7. 各工程について、**実際にどう動いているか(as-is)**を語れる**現場・従業員の一次情報**はありますか？ 想像で埋めている箇所はどこですか？
8. 体験が**崩れる・詰まる箇所（fail point・ボトルネック）**はどこだと感じますか？ それは表側の問題か、裏側のどの工程・誰の担当に原因がありそうですか？
9. 各ステップの**所要時間・成功指標・制約となる規則**、従業員が**フラストレーションを感じる点**はありますか？
10. 見つけた失敗点を、どの**意思決定**（体制変更／システム改修／手順見直し）に、**誰の担当**で接続しますか？

## 具体例（ワークスルー）

対象を一般化した例（架空の数値・企業名は用いない）。あるオンライン学習サービスが、
**無料登録から初回学習開始までで離脱が多い**問題について、表側の痛点を裏側の工程に接続して直すため、
既存のカスタマージャーニー（＝表側）の続き(part two)としてブループリントを描く場面。

- **手順①②目的・スコープ**: 目的=「初回学習の入口で崩れる体験の原因工程を特定し担当を決める」。ペルソナ=「独学したい社会人」、
  シナリオ=「広告流入→無料登録→初回学習開始」の1本に固定。開発・カスタマーサポート・マーケ・インフラの当事者を集める。
- **手順③接地**: 登録後の行動ログ（顧客側）に加え、**サポート担当への聞き取り・オンボーディング処理の観察**で裏側の as-is を収集。
  想像で埋めた工程には「要検証」札を付ける。
- **手順④〜⑥レーンを縦に積む**（段階=登録／初回ログイン／教材選択／学習開始）:
  - 物的証拠: 登録フォーム画面、確認メール、ダッシュボード、最初の教材ページ。
  - 顧客行動: 情報入力→ログイン→何を学ぶか探す→教材を開く。
  - frontstage（見える）: 自動確認メール、ダッシュボードのレコメンド表示。
  - 可視線 —
  - backstage（見えない）: メール配信ジョブ、レコメンド生成バッチ、初期ガイド出し分けロジック。
  - 内部相互作用線 —
  - 支援プロセス: 認証基盤、コンテンツ管理システム、ログ集計・データ基盤、パートナー配信。
- **手順⑦失敗点**: 顧客行動「何を学ぶか探す」の真下をたどると、**レコメンド生成バッチの反映が遅く**、初回ログイン時に
  ダッシュボードが空に近い（＝表側の「何から始めるか分からず放置」の原因が backstage の非同期処理にある）と特定。★を付す。
- **手順⑧高精細化**: 各段階の所要時間、初回学習完了率という指標、個人情報の入力必須項目（規則）、サポートの繁忙点を追記。
- **手順⑨対策・担当**: 失敗点「レコメンド反映遅延」→ 対策: 初回ログイン時は同期でデフォルトの学習パスを即時提示／担当: プロダクト＋データ基盤。
  真因が処理設計にあるため fishbone に渡して深掘り。見直し: 施策後2週・4週。
- **次の一手**: 「初回ログイン時に空でないダッシュボードを出す」を小さく試し、初回学習完了率という仮説を検証してから本実装。
- **未確認の前提**: 離脱の主因が本当に「入口の空白」か「動機の弱さ」か、反映遅延の実測値——社内ログと追加観察で裏取りが要る。

## 相性（組み合わせると効く）

- `customer-journey`: 可視線の**上（顧客から見える体験・感情の谷）**を担う表側の地図。ブループリントはその続き＝**part two**で、
  痛点を可視線の下（従業員・支援プロセス）まで接続する直接の後工程。表→裏の橋渡し。
- `value-stream-mapping`: 可視線の**下の工程**を、リードタイム・在庫・付加価値比で**Lean的に定量改善**する。ブループリントが
  「どの裏工程が詰まるか」を示し、VSMが「その工程をどれだけ速く/ムダなく回すか」を測る（B体験→I工程の接続）。
- `persona`: 1枚に絞る**主語（ペルソナ）**を固める前工程。主語が甘いと全レーンの縦対応がぶれる（手順②の入力）。
- `fmea`: 図上の**失敗点(fail point)を故障モード**として、発生度×影響度×検出度(RPN)で評価し、対策の優先順位を厳密化する後工程。
- `fishbone` / `five-whys`: 「図自体は解を出さない」の穴を埋める。特定した失敗点の**真因**を骨状・なぜなぜで掘り、対策の当てどころを外さない。
- `kpt`: 運用開始後の体験を KPT で振り返り、失敗点の解消状況を継続改善に載せる（作って放置を防ぐ運用の後工程）。
- 揺さぶり枠として `devils-advocate`（「この裏側工程は社内の思い込みで描いていないか」と as-is 接地を疑う）、
  `premortem`（新しい提供体制が失敗する筋を先回り）を添えると、最頻の失敗＝想像で裏側を埋める罠を回避できる。
