# バリューストリームマッピング（VSM）

## 概要

バリューストリームマッピング（Value Stream Mapping / VSM）は、ある製品・サービスを
**「原材料・受注 → 顧客への引き渡し」まで届けるのに必要な全活動（＝バリューストリーム）** を、
**モノの流れ・情報の流れ・タイムライン** の3層で1枚の紙に描き、価値を生む活動と生まないムダ（muda）を
分離して可視化し、改善につなげるリーンの中核ツール。

- **核となる考え方**: 個々の工程を最適化（部分最適）するのでなく、**川上から川下までの「流れ全体」を1枚で俯瞰**し、
  工程間の待ち・在庫・受け渡しに潜むムダを炙り出す。タイムライン下部の「リードタイムのはしご」が、
  **総リードタイム（顧客到達までの総時間）と正味処理時間の比**を可視化し、改善余地を最も直接的に定量化する。
- **現状（Current State）→ あるべき姿（Future State）→ 実行計画** の順で進み、達成後は未来像を新たな現状として
  繰り返す**継続改善**の道具。描くこと自体でなく「流れを設計し直すこと」が目的。
- **出自（諸説の年号・原語は要確認）**: 発祥はトヨタ生産方式(TPS)。トヨタ社内では **「物と情報の流れ図
  （Material and Information Flow Mapping）」** と呼ばれた社内ツールだった。これを **Mike Rother（ミシガン大学で
  トヨタを研究）と John Shook（トヨタに長く在籍）** が初めて体系的に文章化し、**『Learning to See』**（Lean Enterprise
  Institute 刊、初版1998年頃・Shingo賞受賞は1999年とされる）で「Value Stream Mapping」の呼称と手順を確立、トヨタ外へ広めた。
  先行して Womack & Jones が『Lean Thinking』(1996) で "value stream" 概念を普及させたが具体的手順は示していない
  （→出典・要確認項目参照）。

## いつ使う / 使わない

**使う（適する状況）**
- **リードタイムが処理時間より桁違いに長い**プロセス。待ち・在庫・手戻りが多く「作業していない時間」が支配的なとき。
- 原材料/受注から顧客まで**線形に流れる反復的な製品・サービス**の流れを、ドック to ドック（端から端）で俯瞰したいとき。
- **部門・チームをまたぐ受け渡し**で仕事が滞る／どこがボトルネックか、全体像で掴みたいとき。
- リーン変革・カイゼンの**着手前**に、どこを直せば流れが最も改善するか**優先順位**を決めたいとき。
- 製造に限らず、**オフィス業務・サービス・ソフトウェア開発（開発バリューストリーム/DevOps）・医療**などの流れの改善にも応用。

**使わない / よくある誤用（アンチパターン）**
- **描いて終わり**——最頻の失敗。あるべき姿・実行計画・カイゼンに接続しない「文書化作業」に堕ちる。VSMは手段であり目的でない。
- **タクトタイムとサイクルタイムの混同**——欠陥のある未来像マップの最大の原因。タクトは需要側（顧客ペース）、サイクルは供給側（作業時間）。
- **製品ファミリーを絞らない**——全製品/全業務を一度に1枚へ描こうとして破綻する。共通の工程を通る**1ファミリーに限定**する。
- **細部を描き込みすぎる**——情報過多で肝心の流れとムダが埋もれる。まず全体、詳細は必要な工程だけ。
- **現場を歩かず二次データに頼る**——過去データ・他人が採った数字で描く。C/T・段取り・在庫は**自分で現場（gemba）を歩いて実測**する。
- **チーム編成の誤り**——部門横断メンバー・変更権限者・現場作業者が欠けると、絵が正しくならず実行もされない。
- 複数製品で物の流れが共通しない多品種少量、非線形の複雑ネットワーク、財務/経済分析が主目的、単一工程だけの分析、
  品質不良の**真因究明**には不向き。他フレームで補完する（→前提と限界・相性）。

## 前提と限界

- **前提**: 対象の**製品ファミリー（同種の工程・設備を通る製品/サービス群）が1つに定まる**こと。
  ここが曖昧だと1枚に描けず破綻する。加えて、現場でC/T・段取り時間・在庫・稼働率などの実データを採れること
  （採れなければ壁打ちで補うか、まず現場観測から始める）。
- **限界（批判を踏まえて）**:
  - **時間中心で経済指標を持たない**——利益・スループット・コスト・在庫金額などの財務評価は扱えない。「時間のムダ＝金額の改善」とは限らないため、投資対効果は別途評価する。
  - **静的なスナップショット**——描いた瞬間の姿。需要変動や日々のばらつきは1枚に写らない。定期的に描き直す前提で使う。
  - **線形・反復の流れが前提**——多品種少量・非線形・分岐だらけのフローは1枚では捉えきれず、示唆が薄まる。
  - **ムダは見えるが「なぜ」は出ない**——VSMはどこに待ち/在庫があるかを示すが、その原因までは特定しない。
- これらの限界は、**真因は なぜなぜ分析／特性要因図 で掘り、ボトルネックの集中攻略は TOC、各工程のムダ潰しは ECRS、
  実行は PDCA で回す**ことで補える（→相性）。

## 進め方（手順）

命令形で示す。各ステップの「なぜ」を添える。VSMは **選定 → 現状 → あるべき姿 → 計画** の4段で進む。

1. **対象の製品ファミリーとスコープを1つに固定する。** 「誰に・何を届ける、どこからどこまでの流れか」を明文化する
   （例: 受注→出荷、あるいは原材料入荷→顧客納品）。
   なぜ: 対象を絞らないと1枚に描けず、全体を一度に扱おうとして破綻する最頻の失敗に直結する。
2. **顧客と需要を先に置く。** マップ右上に顧客を描き、**タクトタイム＝稼働可能時間 ÷ 顧客需要数**を算出する。
   なぜ: タクトは「どのペースで流すべきか」の基準。ここを供給側のサイクルタイムと混同すると、以降の設計が全部ずれる。
3. **現状マップを、現場を歩いて描く。** 顧客側から**上流へ遡り**、各工程の箱に実データ（C/T・段取りC/O・稼働率・作業者数・
   良品率）、工程間の在庫/仕掛（WIP）、モノの流れ（押し/引き）、情報の流れ（受発注・生産指示）を記入する。
   なぜ: 過去データや伝聞は実態とずれる。自分の足で実測（gemba walk）してこそ、本当のムダが見える。
4. **タイムライン（リードタイムのはしご）を引き、比率を出す。** 各工程の処理時間と工程間の待ち時間を段々に並べ、
   **総リードタイム**と**正味処理時間の合計**、その比（付加価値比率／プロセスサイクル効率 PCE＝正味処理時間 ÷ 総リードタイム）を算出する。
   なぜ: この比率が改善余地を最も直接的に示す。多くの現場で付加価値は数%——「待ち」の巨大さが数字で見える。
5. **ムダの箇所に印をつける。** 大きな在庫滞留・手待ち・作りすぎ・手戻り・過剰な受け渡しを特定し、カイゼンの候補（バースト）を書き込む。
   なぜ: 7つのムダ（作りすぎ・手待ち・運搬・過剰加工・在庫・動作・不良）のうち、VSMは特に**手待ち・在庫・作りすぎ**を炙り出せる。
6. **あるべき姿（Future State）を設計する。** 中核の問いに答えて描く——タクトに各工程を合わせられるか／どこで連続フロー（一個流し）に
   できるか／どこで後補充（プル/スーパーマーケット）にするか／どの1工程をペースメーカーにするか／種類と量をどう平準化するか。
   なぜ: 現状の可視化は起点にすぎない。流れを**設計し直して**初めて改善になる。現状把握と未来像設計は往復する。
7. **実行計画に落とす。** あるべき姿への差分を、担当・期限・目標指標つきのカイゼン項目に分解し、優先順位をつける。
   なぜ: 計画に落とさなければ「描いて終わり」になる。達成したら未来像を新たな現状として、再び手順3から回す（継続改善）。

## 壁打ち質問リスト

各要素を事実で埋めるために、利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す。

1. この流れで**最終的に改善したいこと**は何ですか？（納期短縮／在庫削減／手戻り削減／全体像の把握 など、目的を1つに）
   そして対象の**製品/サービスファミリーと、どこからどこまで**を描きますか？（例: 受注→出荷）
2. その流れの**顧客は誰で、需要はどれくらい**ですか？（数量/期間）——タクトタイムを出すために必要です。
3. 流れを構成する**工程を上流から下流まで**挙げると、いくつ・どんな順番ですか？各工程の担当（人/部門/システム）は？
4. 各工程の**サイクルタイム・段取り替え時間・稼働率・良品率**は分かりますか？現場を歩いて実測したものですか、それとも推定/過去データですか？
5. **工程と工程の間に、どれくらいの在庫や仕掛（待ち）**が溜まっていますか？「モノが止まっている時間」が長いのはどこですか？
6. 生産/作業の**指示はどこから、どう伝わって**いますか？（受注→計画→各工程への情報の流れ、押し出しか後補充か）
7. 体感で**一番のボトルネックや遅延の発生源**はどこだと感じていますか？その根拠（数字・現場の声）はありますか？
8. すでに分かっているデータは何で、まだ**実測できていない前提**は何ですか？（推定と実測を分ける）

## 出力フォーマット

ALWAYS この2段構えで出力する（現状の可視化 → あるべき姿と計画）。テキストで描く場合も、
モノの流れ・情報の流れ・タイムライン・数値の4点を必ず含める。

```
【VSM 現状マップ】対象ファミリー: <…> ／ 範囲: <始点>→<終点> ／ 顧客需要: <…> ／ タクトタイム: <稼働時間 ÷ 需要>
  工程の流れ（上流→下流）:
    [工程A] C/T=__ / C/O=__ / 稼働率=__% / 良品率=__%   →(在庫/待ち: __)→
    [工程B] C/T=__ / C/O=__ / …                          →(在庫/待ち: __)→
    [工程C] …
  情報の流れ: <受注→生産計画→各工程への指示。押し出し/後補充の別>

  炙り出したムダ（手待ち/在庫/作りすぎ/手戻り等）: - <箇所と規模> …

【VSM あるべき姿＋実行計画】
  設計の要点: タクト合わせ / 連続フロー化する区間 / プル(後補充)にする区間 / ペースメーカー工程 / 平準化
  目標: 総リードタイム __→__ ／ 付加価値比率 __%→__%
  カイゼン項目（優先順）:
    1) <どのムダを・どう無くすか>  担当:__  期限:__  目標指標:__
    2) …
【次の一手】<最初に着手する1〜2件と、その効果を測る指標>
【未確認の前提】<実測が要る数値・データ（壁打ちで埋める）>
```

## 具体例（ワークスルー）

対象を一般化した例（架空の数値・企業名は用いない）。**受注生産の小規模メーカーが「納期が長い」原因を流れ全体で捉える**場面。
数値は利用者から実測で得る前提とし、ここでは手順の流れのみ示す。

- **手順①選定**: 目的＝納期短縮。対象＝主力製品ファミリー1つ、範囲＝受注→出荷。
- **手順②顧客・タクト**: 顧客の需要数と稼働可能時間を確認し、タクトタイム（＝どのペースで1個仕上げるべきか）を算出する。
- **手順③現状マップ**: 受注 → 部材調達 → 加工 → 組立 → 検査 → 出荷、と上流へ遡りながら各工程のC/T・段取り・稼働率・良品率を
  現場で実測し、工程間に溜まる仕掛在庫（＝待ち）を書き込む。情報の流れ（受注→計画→各工程への指示）も描く。
- **手順④タイムライン**: 各工程の処理時間は短いのに、**工程間で部材・仕掛が長く滞留**していることが「はしご」で可視化され、
  総リードタイムに対し正味処理時間はごく一部＝付加価値比率が低い、という構図が数字で見える。
- **手順⑤ムダの特定**: 最大の滞留は「加工待ち」と「検査待ち」＝手待ち/在庫のムダ。ここにカイゼン候補の印をつける。
- **手順⑥あるべき姿**: 加工と組立を連続フロー化できないか、検査を工程内に組み込めないか、部材を後補充（プル）にできないか、
  どの工程をペースメーカーにするかを設計し、総リードタイムと付加価値比率の目標を置く。
- **手順⑦実行計画**: 「工程間在庫の上限設定」「段取り時間短縮」等を担当・期限・目標指標つきで優先順位化。まず滞留の大きい区間から着手する。
- **未確認の前提**: 各工程の実C/T・段取り時間・在庫量は**現場実測が必須**。推定のまま描くと未来像が机上の空論になる（実データで裏取り）。

## 相性（組み合わせると効く）

- `toc`: VSMで見えたボトルネック（制約）に集中し、全体スループットを律速する1点を「見つけ・活かし・従属させる」で攻める続き。
- `ecrs`: 特定した各工程のムダを、排除・結合・交換・簡素化の観点で具体的な改善案に落とす（あるべき姿づくりの前工程）。
- `five-whys`: VSMは「どこに」待ち/在庫があるかを示すが「なぜ」は出ない。滞留の**真因**をなぜなぜで掘る補完。
- `fishbone`: 特定した遅延/不良の要因を、人・設備・方法・材料などに分けて構造的に洗い出す。
- `pdca`: あるべき姿への実行計画を、計画→実行→評価→改善で回し、達成後に未来像を新たな現状として繰り返す。
- `lean`: VSMはリーン生産方式の一手法。7つのムダ・平準化・プル等の思想的土台をリーン全体から補う。
- 揺さぶり枠として `premortem`（あるべき姿の実行が失敗する要因を着手前に先回り）を添えると、計画の穴を潰せる。
