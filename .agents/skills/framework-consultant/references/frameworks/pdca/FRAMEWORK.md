# PDCAサイクル

## 概要

PDCAサイクルは、業務やプロセスを **計画(Plan) → 実行(Do) → 評価(Check) → 改善(Act)** の4段階で回し、
1周ごとに標準を引き上げていく**継続的改善（カイゼン）**のマネジメント手法。

| 段階 | 何をするか | 産物 |
|---|---|---|
| **Plan** | 現状把握→目標（あるべき姿とのギャップ）→真因→対策を、測定可能な形で計画する | 目標・指標・対策 |
| **Do** | 計画通りに小さく実行し、データ・記録を取る | 実行結果・実測値 |
| **Check** | 実測を目標・予測と比較し、効いたか／なぜかを検証する | 効果検証・要因 |
| **Act** | 良ければ標準化・横展開、悪ければ修正して次のPlanへつなぐ | 標準化 or 次計画 |

- **核となる考え方**: 科学的方法（仮説→実験→検証→修正）を管理業務に応用したもの。「回して終わり」ではなく、
  1周ごとに標準を更新して**螺旋状（spiral-up）に一段ずつレベルを上げる**のが本質。改善の PDCA に対し、
  維持の **SDCA（Standardize-Do-Check-Act）**が対になる——SDCAで標準を守り、PDCAで標準を引き上げる。
- **出自（諸説あり・要確認）**: 系譜は概ね次の通り。
  (a) **Walter A. Shewhart**（ベル電話研究所）が統計的品質管理の中で
  **仕様→生産→検査**の直線を円環に曲げた「Shewhartサイクル」を示した（著書1939年とされる）。
  (b) **W. Edwards Deming** がこれを改変し、1950年に日本科学技術連盟（日科技連, JUSE）の講義で
  **設計→生産→販売→再設計**の「デミング・ホイール」を紹介。
  (c) この講義を聞いた**日科技連の幹部（氏名は特定されていない）**が Plan-Do-Check-Act に再構成し、
  **石川馨**らが整理・普及した——というのが通説。**PDCAは主に日本で発展・定着**した枠組みで、Deming本人の考案語ではない。
  なお**Deming自身は晩年PDCAを嫌い**、"Check" は "hold back（止める）" の含意で合否確認に矮小化されるとして、
  第3段階を**学習(Study)**に置く **PDSA（Plan-Do-Study-Act）**を推奨した（→前提と限界／出典）。

## いつ使う / 使わない

**使う（適する状況）**
- 施策や改善が**やりっぱなしで定着しない**、効果があったのか分からない——効果検証と標準化の型を入れたいとき。
- 製造・品質・オペレーション・営業活動など、**反復性があり測定できる**業務を地道に良くしたいとき。
- 品質不良・ミス・クレームの**再発を止めたい**（対処療法でなく、標準を更新して固定したい）とき。
- KGI/KPIや目標は決めたが**運用が空回り**している——目標を回る仕組みに落としたいとき。
- QCサークル・改善活動・PJの**振り返り(Check)と次アクション**を規律化したいとき。

**使わない / よくある誤用（アンチパターン）**
- **Check/Actを飛ばす**——最頻の失敗。実行して「やった気」になり効果検証も標準化もしない → 一発対処に堕し再発する。
  Check（効いたか・なぜか）とAct（標準化 or 修正）まで回して初めてPDCA。
- **Planの作り込み不足**——問題定義が曖昧、真因分析を飛ばして解決策に飛びつく → 症状対処に終わる。目標が測定不能。
- **回すのが遅い・重い**——1周に時間をかけ過ぎ、環境変化に追随できず「計画倒れ」。速く小さく回す。
- **標準化(Act)の欠如**——改善が個人技で終わり、横展開・仕組み化されず消える。良い結果ほど標準に落とす。
- **目標の不整合**——関係者が別々のゴールを持つと問題解決が空回りする（PDCAの弱点として指摘される）。
- **前例のない不確実・高速局面での固執**——状況が刻々変わる領域では計画が陳腐化する。OODA等が向く（→相性）。
- ゼロイチの破壊的創造や、1回限りで反復のないタスク、成功指標が定義できない探索初期には不向き。

## 前提と限界

- **前提**: (1) **測定可能な目標**が置けること（Checkが成立しない曖昧なテーマには使えない）。
  (2) **反復性**があること（次周に学びを渡せる業務）。(3) 実行のデータ・記録が取れること（Doの記録がCheckの材料）。
  無ければ壁打ちで目標と指標を先に固める。
- **限界（批判を踏まえて）**:
  - **事後修正的**——初期計画後は発散しにくく、予防や革新を促しにくい（反応的との批判）。ゼロイチ発想は別枠で補う。
  - **速度の問題**——1周が重いと環境変化に負ける。不確実・即応の局面では **OODA（Observe-Orient-Decide-Act）**が
    有利で、「PDCAは時代遅れ」論の背景になっている。反復性と速度で使い分ける。
  - **"Check" の矮小化**——Deming は "Check" を嫌い、第3段階を**学習(Study)**とする **PDSA** を推奨した。
    本スキルでも Check を「計画通りできたかの確認」に留めず、**予測と実測を比較し理論(仮説)を修正する学習**として扱う。
  - **維持と混同しない**——標準を「守る」局面はSDCA、「上げる」局面はPDCA。両者を切り分けないと改善が空回りする。
- これらは **Planの真因分析をなぜなぜ分析／特性要因図で強化する / 高速局面はOODAへ切替える /
  標準化をSDCAで固める** ことで補える（→相性）。

## 進め方（手順）

命令形で示す。各ステップの「なぜ」を添える。**Plan に最も時間をかける**（PDCAの成否はPlanで決まる）。

1. **テーマとゴールを1つに固定する。** 何の業務・指標を、いつまでに、どの水準にするかを「あるべき姿とのギャップ」で明文化する。
   なぜ: 目標が測定不能だとCheckが成立せず、ループが学習を生まない。
2. **【Plan】現状を把握し、真因を分析する。** データで現状を掴み、なぜギャップが出るのかを掘る（なぜなぜ分析／特性要因図）。
   なぜ: 真因を外すと対策が症状対処になり、何周回しても再発する。
3. **【Plan】対策を仮説付きで具体化する。** 「なぜ効くはずか」の仮説と、5W1H・担当・期限・**成功指標(KPI)**まで落とす。
   複数案を検討し、一案に賭けない。なぜ: 仮説がないと Check で「効いた／効かない」の理由を学べない。
4. **【Do】小さく実行し、記録を取る。** まず限定範囲で試し、実測値・逸脱・気づきを記録する。
   なぜ: 大規模に一発勝負すると失敗コストが高く、Checkの材料も残らない。
5. **【Check】予測と実測を比較し、要因まで検証する。** 目標に届いたか、**なぜその結果になったか**を分析する。
   「計画通りに実行できたか」の確認に留めず、方針・目標に照らした方向性のズレも見る。
   なぜ: ここが学習(Study)の本体。合否だけ見て理由を問わないと改善が積み上がらない。
6. **【Act】結果に応じて分岐し、次周へつなぐ。**
   - **効果あり → 標準化・横展開**: 手順書・チェックリスト・仕組みに落として定着（SDCAへ渡す）。
   - **効果なし/不十分 → 計画を修正**: 真因の見立てや対策を見直し、次のPlanに反映。
   なぜ: 良い結果を標準化しないと個人技で消え、悪い結果を放置すると学びが失われる。
7. **次の周回でレベルを一段上げる。** 更新した標準を出発点に、次のギャップへPDCAを回す。
   なぜ: PDCAは1周で完結しない。螺旋状に回してこそ継続的改善になる。

## 壁打ち質問リスト

各段階を埋めるために利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す。

1. この改善で**最終的に達成したい状態**は何ですか？ それは**どの指標で、いつまでに、どの水準**だと「成功」と言えますか？（測定可能な目標＝Checkの前提）
2. 今の**現状の数値・事実**は何ですか？ あるべき姿とのギャップはどれくらいですか？（推測でなくデータで）
3. そのギャップが生じている**原因**はどこにあると見ていますか？ 真因まで掘れていますか、それとも症状ですか？
4. 打とうとしている対策は**「なぜ効くはず」か（仮説）**を説明できますか？ 対策は1案だけですか、他の選択肢は検討しましたか？
5. 実行した結果を**何のデータで、いつ、誰が確認**しますか？ 効果を測る仕組みは用意できていますか？（Check/Actの実行主体）
6. 過去に似た施策を**やりっぱなしにした**ことはありますか？ 今回、効果が出たら**どう標準化・横展開**しますか？
7. このテーマは**反復性があり計画が立てられる**ものですか、それとも状況が速く変わり計画が陳腐化しやすいものですか？（PDCA向きか、OODA向きかの判定）

## 出力フォーマット

ALWAYS この型で出力する（1周を設計する2段構え。回した後は【Check以降】を追記して螺旋を継続する）。

```
【PDCA設計】テーマ: <対象業務・指標> ／ ゴール: <いつまでに・どの指標を・どの水準に>

Plan:
  - 現状/ギャップ: <データに基づく現状 → あるべき姿との差>
  - 真因: <なぜギャップが出るか（真因。症状と区別）>
  - 対策(仮説): <打ち手＋「なぜ効くはずか」＋代替案の検討>
  - 成功指標/期限/担当: <KPI ・ 期限 ・ 実行/確認の主体（5W1H）>
Do:
  - 実行範囲: <まず小さく試す範囲> ／ 取るデータ: <Checkの材料>
Check:
  - 予測 vs 実測: <目標比・達成/未達> ／ 要因: <なぜその結果か>
Act:
  - 効果あり → 標準化/横展開: <手順書・仕組み化の内容>
  - 効果なし → 修正: <見直す真因/対策 → 次のPlanへ>

【次周への申し送り】<更新した標準 ・ 次に上げるべきギャップ>
【未確認の前提】<データ確認が要る点（壁打ちで埋める）>
```

## 具体例（ワークスルー）

対象を一般化した例（架空の数値・企業名は用いない）。あるコールセンターで「一次解決率が低く再入電が多い」問題を改善する場面。

- **テーマ/ゴール**: 一次解決率を、一定期間内に現状より引き上げる（水準と期限は現場データで設定）。
- **Plan / 現状・真因**: 応対ログを集計して再入電の多い問い合わせ類型を特定。なぜなぜ分析で、
  「オペレーターが手順を検索できず保留・折り返しになる」ことが真因の一つと見立てる（＝知識の在り処が真因、応対態度は症状）。
- **Plan / 対策(仮説)**: 「頻出問い合わせのFAQを検索しやすく整備すれば、その場で解決でき一次解決率が上がる」という仮説。
  対策は「FAQ整備」に加え「トークスクリプト改訂」も候補として比較し、まずFAQ整備から着手。成功指標＝一次解決率、期限・担当を設定。
- **Do**: 対象を一部のチーム／一部の問い合わせ類型に限定して試行。解決/再入電の別を記録する。
- **Check**: 試行チームの一次解決率を非試行と比較し、上がったか・なぜかを検証。上がった類型と効果の薄い類型を切り分ける。
- **Act**: 効果が出た類型は FAQ とその運用を**標準化して全チームへ横展開**（SDCAで維持）。効果の薄い類型は
  真因の見立て（本当にFAQ不足が原因か）を見直し、次のPlanへ回す。
- **次周への申し送り**: 更新した標準を出発点に、次に効きそうなギャップ（例: 別類型／別チーム）へPDCAを継続。
- **未確認の前提**: 再入電の定義・集計方法、対象期間の妥当性——ここは実データで裏取りが要る（推測のまま進めない）。

## 相性（組み合わせると効く）

- `five-whys`: Plan/Checkの**真因追究**を担う。「なぜギャップが出るか」を掘り、症状対処を防ぐ直接の道具。
- `fishbone`: Checkでの**要因の網羅整理**（人・方法・設備・材料等）。真因分析の抜け漏れを防ぐ。
- `kgi-kpi-okr`: Planの**目標・成功指標の設計**を精緻化し、Checkが成立する測定可能なゴールを与える。
- `qc-story`: PDCAを**品質改善の標準手順**に型化したもの。改善活動を定型フローに乗せたいときの上位版。
- `toc`: 改善対象を**ボトルネック（制約）に絞る**視点。全部を等しく回さず、効く一点にPDCAを集中させる。
- 揺さぶり枠として `premortem`（Planの段階で「この改善が失敗するとしたら」を先回りし、対策を厚くする）や、
  `ooda`（不確実・高速で状況が変わる局面では、PDCAの代わりに高速の状況判断ループへ切り替える対比枠）を添えると視点が増す。

**要ファクトチェック（Web調査で誤りが混入しやすい断定）**
- Shewhartサイクルの初出年（著書1939年『Statistical Method from the Viewpoint of Quality Control』とされるが要確認。1920年代とする記述もある）。
- Demingの来日・日科技連講義の年（1950年／1951年が併記される）と、紹介したホイールの正確なラベル（設計→生産→販売→再設計）。
- **PDCAへ再構成した「日科技連の幹部」は氏名が特定されていない**（通説。個別の人名帰属は避ける）。石川馨の関与（整理・普及、6ステップ化の年=1980年代とされるが要確認）。
- Demingが "Check" を嫌いPDSAを推奨した経緯（1986年の講演での批判、著書『The New Economics』1993年での定式化）の書誌・年号。
- 各段階の和名（計画/実行/評価/改善）や「Act=Action/Adjust」の表記ゆれは実務慣用で、原典英語ラベルと厳密一致しない場合がある。
- SDCA・OODAとの対比は解説上の整理であり、PDCA原典に明記された対概念ではない。
