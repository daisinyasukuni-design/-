# シックスシグマ（Six Sigma / DMAIC）

## 概要

シックスシグマは、**プロセスのばらつき(variation)と欠陥(defect)の原因を、データと統計で特定・除去し、
品質を安定させる**改善方法論。核心は次の3点。

- **ばらつきこそ品質の敵** — 平均が良くても、ばらつけば規格を外れて不良になる。狙うのは「平均を動かす」より「ばらつきを締める」。
- **感覚でなくデータで真因を突く** — 「たぶんこれが原因」で対策せず、測定→統計的検証で真因(X)を絞ってから手を打つ。
- **改善を仕組みで定着させる** — 直して終わりにせず、管理図・標準化・ポカヨケで**元に戻らない状態**を作る。

**名前の由来（統計）**: 「シグマ(σ)水準」は、工程平均から最も近い規格限界までに標準偏差が何個入るかの尺度。
高いほどばらつきに余裕がある。**6σ = 100万機会あたり欠陥 3.4 件(3.4 DPMO)以下**を目標水準とする
（長期の平均ドリフトを見込んだ「1.5σシフト」を織り込んだ値。詳細は `references/tools-and-stats.md`）。

**共通の解き方（DMAICのプリズム）**: 問題を直接いじらず、① 問題と顧客要求を**定義**し → ② 現状を**測り** →
③ ばらつきの**真因(X)を統計で特定**し → ④ 打ち手を**検証して改善**し → ⑤ 効果を**管理して定着**させる。
「Y = f(X)（結果Yはいくつかの原因Xの関数）」——効くXを見つけて締める、が背骨。

- **出自（要確認・断定回避）**: 1980年代、米**モトローラ**で誕生。エンジニアの **Bill Smith（ビル・スミス）** が
  「Six Sigma」を考案・命名（1986年頃とされる）。**Mikel Harry（マイケル・ハリー）** が方法論として体系化
  （原型 MAIC → 後に Define を加え DMAIC）。1995年頃、**GE**が**ジャック・ウェルチ**のもと全社導入し世界へ普及した、
  という筋は各資料で概ね一致するが、**年号・金額・「考案/命名/体系化」の役割分担は資料で食い違う**（→出典・要確認）。

**このスキルは大物。** DMAICの各フェーズと主要ツールは `references/` に退避する。FRAMEWORK.md本体は
「概要＋どのフェーズ/ツールをいつ使うか＋壁打ち」に絞る。**まず本体で"今どのフェーズか"を診断し、必要な reference を読み込んで適用する。**

## いつ使う / 使わない

**使う（適する状況）**
- **反復するプロセス**で、不良率・歩留り・リードタイム・コスト・クレームなどに**ばらつきや欠陥**があるとき。
- **真因が不明**で、感覚でなく**データ・統計で原因(X)を突き止めたい**とき（仮説検証が要る）。
- 過去に**対策してもすぐ元に戻る**——再発防止・**定着(Control)**まで面倒を見たいとき。
- **工程能力(Cp/Cpk)やシグマ水準を上げたい**、規格外れを構造的に減らしたいとき。
- データが取れる/取る価値があり、腰を据えて（数週間〜数か月）取り組める重要テーマのとき。

**使わない / よくある誤用（アンチパターン）**
- **真因が既に分かっている問題に統計を回す**——最頻の過剰適用。原因が明白なら即実行(Justdoit)やカイゼンが速い。
  問題の大半は基本的なQC手法で解けるとされ、フル方法論は最も複雑な少数の問題向け。
- **創造・発散・新規事業に使う**——DMAICは**既存プロセスの最適化**に特化。破壊的イノベーションはむしろ阻害しうる
  （既存の枠を締める道具なので、0→1の探索には不向き）。発想は発散系フレームへ。
- **一度きり/緊急/データが取れない問題**——測定に土台がないと空回りする。母集団が小さすぎる/観測できない対象も不適。
- **測定システムを疑わず分析へ進む**——測り方(MSA/Gage R&R)が甘いと、ばらつきの正体が「測定誤差」なだけの誤診に陥る。
- **ツールのための分析**——DOEや高度な検定を"見せ場"にして目的を見失う。統計は真因特定の手段であって目的ではない。
- **Controlを省く**——改善だけして仕組み化しないと必ず戻る。管理図・標準化・ポカヨケまでやって初めて完了。
- **投資対効果を無視した小テーマ**——ベルト人材・訓練・工数の負荷が重い。効果が小さい問題に大掛かりに回さない。

## 前提と限界

- **前提**: 対象が**反復可能で測定できるプロセス**であること。改善したい**結果指標(Y)**が数値で定義でき、
  データが取れる（または取りにいける）こと。腰を据えた期間と、最低限の統計リテラシー/推進体制があること。
  これらが欠けるなら壁打ちで補うか、まず QC7つ道具・PDCA・特性要因図で足場を作る。
- **限界（批判を踏まえて）**:
  - **イノベーション阻害** — 既存プロセスの分散最小化に最適化されており、新規創造・探索を締め付けうる（GE/3M で創造性を殺したとの批判）。
  - **統計への過度の依存** — ばらつき低減に偏り、そもそもの価値・ロバスト設計・顧客の本質ニーズを見落としがち。
  - **重い運用コスト** — ベルト制度・訓練・工数が前提で、小組織や小テーマには過剰。プロジェクトの失敗率が高いとの調査もある（多くは経営コミット不足・テーマ選定ミス・変革管理欠如が原因）。
  - **1.5σシフトの妥当性論争** — 3.4 DPMO の根拠となる 1.5σ ドリフト仮定は「恣意的」との批判（統計家 D. Wheeler ら）。数値目標を金科玉条にしない。
  - **データ品質依存** — 測定システムが甘い/データが不整合だと、丸ごと誤った結論に至る。
- これらは、**テーマ選定を戦略に紐づける／Measureで測定系を先に検証する／Leanでムダと流れも併せて見る／
  Controlまで完走する／数値目標を目的化しない**ことで補える（→相性・手順）。

## 進め方（手順）

命令形で示す。各ステップの「なぜ」を添える。詳細な各フェーズの成果物・ツールは `references/dmaic-phases.md`、
道具の選び方と統計は `references/tools-and-stats.md` を読み込んで使う。**まず"今どのフェーズにいるか"を診断してから入る。**

1. **改善したい結果指標(Y)と問題を、数値と顧客価値で定義する【Define】。** 何が/どれだけ悪いか（不良率○%、リードタイム○日のブレ等）、
   顧客が本当に求める品質特性(CTQ)は何かを言語化し、範囲・目標・体制を確定する。成果物: プロジェクト憲章・SIPOC。
   なぜ: 問題と成功条件が曖昧だと全工程が空回りする。「何を6σ化するのか」を1つに絞る。
2. **現状を測り、ベースラインを出す【Measure】。** データ収集計画を立て、**測定システム(MSA/Gage R&R)を先に検証**したうえで、
   現在の工程能力(Cp/Cpk)・シグマ水準・DPMOを算出する。なぜ: 出発点を数値で固定しないと、改善したかどうか判定できない。測り方が甘いと以降が全部崩れる。
3. **ばらつきの真因(X)を統計で絞る【Analyze】。** 特性要因図・なぜなぜで候補Xを洗い、パレートで的を絞り、
   仮説検定(t検定/ANOVA)・相関/回帰・（必要ならDOE）で「本当に効くX」を実証する。なぜ: 思い込みのXを潰すのが本methodの肝。Y=f(X)の効くXだけに手を打つ。
4. **効くXへの打ち手を設計し、検証する【Improve】。** 対策案を出し、DOEやパイロットで効果を実データで確かめる。
   ポカヨケ(mistake-proofing)で「ミスできない」設計にする。なぜ: 本番展開の前に小さく実証し、副作用も点検する。効果が数値で出ない対策は採らない。
5. **改善を仕組みで定着させる【Control】。** 管理図(SPC)で工程を監視し、標準作業(SOP)・管理計画・ポカヨケで**元に戻らない**状態を作り、担当へ引き継ぐ。
   なぜ: 改善は放置すると必ず戻る。ここまでやって初めてプロジェクトは完了する（最頻の未完＝Control省略）。
6. **効果を検証し、横展開と次テーマに繋ぐ。** ベースライン比で工程能力の改善を確認し、他ラインへ展開できるか、次に締めるべきばらつきは何かを決める。
   なぜ: 6σは1回で終わらない継続活動。学びを他工程に効かせる。
7. **（新規設計なら）DMADVへ切り替える。** 既存プロセスが無い/根本再設計なら、Define→Measure→Analyze→**Design→Verify** で最初から6σ品質を織り込む。
   なぜ: 既存改善(DMAIC)と新規設計(DMADV)は土俵が違う。無理に既存改善で作らない。

## 壁打ち質問リスト

各要素を事実で埋めるために、利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す。

1. 改善したい**結果(Y)**は何ですか？（不良率／歩留り／リードタイム／クレーム件数／原価 など）今それは**数値でいくつ**で、**目標**はいくつですか？
2. その品質は、**顧客/後工程が本当に困っている点(CTQ)**とどう結びついていますか？「良い/悪い」の判定基準は何ですか？
3. これは**反復するプロセス**の問題ですか、それとも一度きり/新規のことですか？（DMAICか、Justdoitか、DMADVかの分岐）
4. 今この問題は**DMAICのどの段階**にいますか？（問題が曖昧＝Define／数値が無い＝Measure／真因不明＝Analyze／対策検証中＝Improve／戻り防止＝Control）
5. **データは取れますか**？ 誰が・いつ・どう測っていますか？ その**測り方は信用できますか**（測定者や機器で数値がぶれませんか＝MSA）？
6. ばらつき・不良の**原因として疑っている要因(X)**は何ですか？それは**事実/データで裏づけ**られていますか、それとも印象ですか？
7. 過去に打った対策と、それが**効かなかった/元に戻った理由**は何ですか？（Controlの弱さや真因の取り違えを探る）
8. この改善に割ける**期間・人・スキル**はどれくらいですか？（重いフル方法論に見合う重要テーマか、軽いカイゼンで十分かの判断）

## 具体例（ワークスルー）

対象を一般化した例（架空の数値・企業名は用いない）。**部品の塗装工程で「塗膜厚が規格から外れる不良が一定率で出続ける」**を締めたい場面。
数値は入れず、DMAICの流れと判断の型を示す（実データは現場で測って埋める）。

- **【D 定義】**: Y=「塗膜厚が規格外となる不良率」。顧客CTQ=「見た目のムラと防錆性能」。範囲は当該塗装ライン1本、目標は不良率を現状から半減、と一文で固定。SIPOCで供給者〜顧客と主要工程を俯瞰。
- **【M 測定】**: まず膜厚計の**測定システムを検証(MSA)**——測定者や測定位置で数値がぶれないか。信頼できると確認後、一定期間データを取り、**ベースラインの工程能力(Cp/Cpk)とシグマ水準**を算出（今どれだけ悪いかを数値で固定）。
- **【A 分析】**: 特性要因図となぜなぜで候補X（塗料粘度・ガン距離・搬送速度・室温湿度・オペレータ）を洗う。パレートで不良の偏りを見て的を絞り、**仮説検定/回帰**で「膜厚のばらつきに本当に効くX」を実証（例: 印象では"オペレータ差"でも、データ上は"塗料粘度と室温"が主要因、という取り違えをここで潰す）。
- **【I 改善】**: 効くX（例: 粘度・温度）に対し、**DOE**で最適な設定条件を探索し、**パイロット**で規格内に収まるかを実データで確認。狙い外の設定を物理的に選べないよう**ポカヨケ**（治具・インターロック）を設計。
- **【C 管理】**: 塗膜厚を**管理図(SPC)**で監視し、外れの兆候を早期に検知。最適条件を**標準作業(SOP)**と管理計画に落とし、現場へ引き継ぐ。改善後の工程能力をベースラインと比較して効果を確認。
- **【次の一手】**: まずMSAを実施し測定系を確定する（ここが未検証だと以降が全部揺らぐため最優先）。
- **【未確認・要データ】**: 現状の不良率・工程能力の実測、疑っているXの寄与——いずれも実データで裏取りが要る（推測のまま進めない）。

## 相性（組み合わせると効く）

- `lean`: ムダ・流れ・スピードのLeanと、ばらつき・品質のSix Sigmaは補完的。統合運用（Lean Six Sigma）で「速く・安定して」を両取りする最良の相方。
- `fishbone`: Analyzeで真因の候補X（4M等）を構造的に洗い出す定番ツール。DMAICのA段にそのまま埋め込む。
- `five-whys`: 特性要因図で挙げた要因を深掘りし、表層でなく真因まで掘るAnalyzeの相方。
- `pdca`: 軽量な改善はPDCAで速く回す。真因不明・要統計・要定着の重いテーマだけDMAICへ、という使い分けの対。
- `toc`: 制約(ボトルネック)理論で「どの工程を6σ化すべきか」の**テーマ選定**を全体最適の視点で絞る。効かない所を締める過剰投資を防ぐ。
- `value-stream-mapping`: 工程全体のムダと停滞を可視化し、Six Sigmaで攻める対象工程を特定する前工程。
- `kgi-kpi-okr`: Yの目標値とCTQを、事業のKGI/KPIに接続してテーマの重要性と効果を測る。
- 揺さぶり枠として `premortem`（改善策が"元に戻る"失敗シナリオを先回りしControlを厚くする）や `devils-advocate`（「その真因Xは本当か、測定誤差では？」と分析の思い込みを突く）を添えると、統計偏重の盲点を補える。
