# リーンキャンバス

## 概要

リーンキャンバスは、新規事業やスタートアップのアイデアを **9つのブロック**で1枚に可視化し、
事業モデルを「**検証すべき仮説の集合**」として捉えるツール。狙いは完成した計画書を作ることではなく、
**リスク（不確実性）の高い前提**を素早くあぶり出し、検証（学習）の起点にすること。
Ash Maurya はリーンキャンバスを完成した計画書ではなく『検証すべき仮説の集合』と位置づける。

| 左（製品側） | 中央 | 右（市場側） |
|---|---|---|
| 課題(Problem) | 独自の価値提案(UVP) | 圧倒的な優位性(Unfair Advantage) |
| ソリューション(Solution) | （＋ハイレベルコンセプト） | チャネル(Channels) |
| 主要指標(Key Metrics) | | 顧客セグメント(Customer Segments) |
| コスト構造(Cost Structure) | | 収益の流れ(Revenue Streams) |

- **核となる考え方**: スタートアップの失敗は「実行」より「**間違ったものを作る**」ことに起因する。
  だから Problem / Customer を起点に、最もリスクの高い前提から検証し、証拠に応じて仮説を書き換え続ける。
- **出自（要確認・断定回避）**: 考案は **Ash Maurya**。2010年頃のブログ記事で初出し、著書
  *Running Lean*（O'Reilly、第1版は2012年とされる）で体系化したと紹介される（年号は要確認）。
  原型は Alexander Osterwalder らの **ビジネスモデルキャンバス(BMC)**。Maurya は「箱を1つ足すたびに
  1つ消す」自己制約で、**BMCの9ブロックのうち4つを差し替えた**——
  削除: Key Partners / Key Activities / Key Resources / Customer Relationships、
  追加: Problem / Solution / Key Metrics / Unfair Advantage。対象読者は「起業家」で、
  記述用途のBMCに対しリーンキャンバスは**アイデアを素早く検証する**用途に振っている（→出典）。

## いつ使う / 使わない

**使う（適する状況）**
- 新規事業・スタートアップの**ごく初期**に、アイデア全体を1枚で俯瞰し前提を洗い出したいとき。
- 「何から検証すべきか」が分からず、**リスクの高い仮説の優先順位**をつけたいとき。
- 顧客の**課題**と提供する**価値**が噛み合っているか（Problem-Solution Fit）を点検したいとき。
- **ピボット**の検討や、チーム／メンターへ事業構想を**手短に共有**したいとき。
- 複数のアイデアを同じ器で並べ、**素早く比較・淘汰**したいとき（1枚20分で描ける軽さが武器）。

**使わない / よくある誤用（アンチパターン）**
- **一度書いて放置する**——最頻の失敗。仮説ボードなのに固定計画として扱う。証拠が出るたびに
  反証された箱を消し、検証された箱を確定させ、**更新し続ける**のが本来の使い方。
- **Problem を飛ばして Solution に飛びつく**——解に恋してしまう典型。設計思想（課題起点）を無視すると、
  誰も困っていないものを作る。
- **Problem / UVP / Customer Segments が曖昧・広すぎる**——「万人向け」「業務を効率化」等は反証不能
  （untestable）で検証できない。狭く・具体的に書く。UVPは「非技術者の他人に読み上げ、説明し返せるか」で検査。
- **Unfair Advantage を無理に埋める／捏造する**——多くの初期スタートアップは最初これが空でよい。
  「容易に買えない・真似できない」ものだけを書き、無ければ空欄のまま「今後築く対象」として扱う。
- **一人・机上で完結する**——顧客と話さず思い込みで埋める。外部フィードバックで裏を取る前提で使う。
- **詳細な財務計画・確立事業の全体設計**には不向き。数値の裏取りや確立事業はBMC/事業計画で補完する（→限界）。

## 前提と限界

- **前提**: 対象アイデア（事業／製品）が1つに定まっていること。検証を回す意思（顧客と話す、実験する）が
  あること。無ければ穴埋めが机上の空論に堕ちる。1枚に**完璧を求めない**——まず20分でスナップショットを取り、
  空欄は空欄のまま残してよい。
- **限界（批判・考案者自身の指摘を含む）**:
  - **数字・トラクションが弱い**——Maurya 自身が「リーンキャンバスは事業計画の代替には**足りない**」と述べ、
    投資家が求める「問題が十分大きいか」の定量面を補う **Customer Factory Blueprint**（海賊指標系の指標）と
    **Traction Roadmap** を別途提唱している。財務・成長の数値は別ツールで補う前提。
  - **Key Resources / Key Partners の箱が無い**——必要な資源・提携の検討が抜けやすい。意図的な簡素化の裏返し。
  - **拡大・確立フェーズには向かない**——検証済みでスケールする段階では、記述・整合に強いBMCや事業計画へ移る。
  - **1枚では因果や競争構造の深掘りができない**——外部環境はPEST/5フォース、価値の噛み合わせはVPCで補完する。
- これらは、**財務はTraction系ツールで補う／確立事業はBMCへ／価値の噛み合わせはVPCへ／
  検証はMVPへ渡す**ことで補える（→相性）。

## 進め方（手順）

命令形で示す。各ステップに「なぜ」を添える。Maurya は「唯一正しい記入順は無い」と述べるため、
順序は目安とし、**riskの高い前提を先に検証する**という原則を優先する。

1. **アイデアの発端（backstory）を明記し、対象を1つに固定する。** この着想は「課題起点／解法起点／
   外部指示」のどれか。なぜ: 最初に埋める箱に自分のバイアスが出る。発端を自覚すると盲点が見える。
2. **顧客セグメントと課題を「対」で先に置く。** 対象顧客（+最初に使う理想像=アーリーアダプター）と、
   その上位1〜3の課題を書く。各課題の下に **既存の代替手段(Existing Alternatives)**——今それがどう
   解決されているか——を書く。なぜ: 課題は「人」の文脈でしか存在せず、真の競合は既存の代替行動だから。
3. **独自の価値提案(UVP)を1文で書く。** 「なぜ違い、注目に値するか」を single, clear, compelling な
   メッセージに。補助として **ハイレベルコンセプト**（「◯◯における△△」型のアナロジー）を添える。
   なぜ: 曖昧なUVPは検証不能。他人に読み上げて説明し返せるかで質を測る。
4. **ソリューションを、各課題に対応する上位3機能として書く。** 作り込みすぎない（箱を小さく保つ）。
   なぜ: 最初の解に固執させないため。MVP思想で「最小限、後で捨てられる」前提にする。
5. **チャネル・収益の流れ・コスト構造を埋める。** 顧客への経路、収益モデル、特定マイルストーンまでの
   主なコスト。なぜ: 事業として回るかの粗い成立条件を見る（ここは後で数値ツールで精緻化）。
6. **主要指標(Key Metrics)を1つに絞る。** 事業の健全性を表す単一のマクロ指標を選ぶ。
   なぜ: 多指標は焦点を失う。「今どこを見れば良し悪しが分かるか」を1つに定める。
7. **圧倒的な優位性(Unfair Advantage)を、真似・購入が困難なものだけ書く。** 無ければ空欄で可。
   なぜ: 無理に埋めると自己欺瞞になる。空欄は「今後築く対象」を示す健全なシグナル。
8. **各ブロックをリスクで採点し、検証順を決める。** 「外れたら事業が崩れる／確証が薄い」前提から
   優先的に実験・顧客対話で検証する。なぜ: キャンバスはゴールでなく**検証計画の起点**。ここで止めない。

## 壁打ち質問リスト

各ブロックを事実で埋めるために、利用者へ投げ返す問い。空欄は勝手に埋めず、まずこれで引き出す。

1. この事業で**狙う顧客は誰**で、最初に使ってくれそうな理想像（アーリーアダプター）はどんな人ですか？
   「万人」ではなく、できるだけ狭く言うと？
2. その顧客が抱える**上位3つの課題**は何ですか？そして今、彼らはその課題を**どう凌いでいます**か
   （既存の代替手段・回避策・我慢）？
3. あなたの提供価値を、**製品を知らない他人に一文で言って伝わる**ように言うと何ですか？
   「なぜ既存の代替手段でなく、あなたを選ぶ」のですか？
4. その価値を成り立たせる**最小限の機能を3つ**挙げると？逆に、無くても検証できる機能はどれですか？
5. この事業の**成否を1つの数字で測る**なら、どの指標を見ますか？（登録数／継続率／紹介数など）
6. 競合が**容易に真似・購入できない**強みはありますか？（無ければ「今は無い」で構いません。何を今後築きますか？）
7. これらの前提のうち、**外れたら事業が根本から崩れるほど重要で、かつ今いちばん確証が薄い**のはどれですか？
8. すでに**顧客と話して確かめた**ことと、まだ**あなたの思い込みのまま**の前提は、それぞれ何ですか？

## 出力フォーマット

ALWAYS この2段構えで出力する（キャンバス→検証計画）。埋まらない箱は「（未検証／要ヒアリング）」と明記し、
勝手に埋めない。

```
【リーンキャンバス】対象アイデア: <一つに固定> ／ 発端: <課題起点/解法起点/外部指示>
  顧客セグメント:  <対象顧客>（アーリーアダプター: <理想像>）
  課題(上位3):     1.<…> 2.<…> 3.<…>  ／ 既存の代替手段: <今どう凌いでいるか>
  独自の価値提案:  <一文の説得メッセージ>（ハイレベルコンセプト: <「◯◯の△△」>）
  ソリューション:  <各課題に対応する上位3機能>
  チャネル:        <顧客への経路>
  収益の流れ:      <収益モデル・価格>
  コスト構造:      <主なコスト（特定マイルストーンまで）>
  主要指標:        <成否を測る単一のマクロ指標>
  圧倒的な優位性:  <真似・購入が困難なもの／無ければ「現時点で無し（今後築く）」>

【検証計画（リスク順）】
  最優先で検証する前提: <外れたら崩れる×確証が薄い前提>
    → 検証方法: <顧客対話/実験/MVP など> ／ 成功の判定: <何が起きたら仮説OKか>
  次に検証する前提: <…>
【次の一手】<今週着手する1〜2個の検証アクション>
【未確認の前提】<顧客と話せていない前提を明示（推測と事実を分ける）>
```

## 具体例（ワークスルー）

対象を一般化した例（架空の数値・企業名は用いない）。地方在住のフリーランス向けに、経費・請求管理を
簡単にするアプリのアイデアを検討する場面。

- **手順①発端**: 発端は「解法起点」（先にアプリを思いついた）と自覚 → 課題の裏取りが手薄という盲点に注意。
- **手順②顧客×課題**:
  - 顧客セグメント: 開業間もない個人フリーランス（アーリーアダプター: 確定申告が初めてで会計知識が乏しい層）。
  - 課題(上位3): (1)経費の記録が続かない (2)請求書作成に手間取る (3)確定申告時にまとめて慌てる。
  - 既存の代替手段: 表計算ソフトへの手入力、紙の領収書を封筒にため込む、申告期だけ税理士に丸投げ。
- **手順③UVP**: 「簿記を知らなくても、レシート撮影だけで確定申告まで迷わないフリーランス向け経費アプリ」。
  ハイレベルコンセプト: 「個人事業主のための"撮るだけ経理"」。
- **手順④ソリューション**: (1)レシート撮影の自動仕訳 (2)ワンタップ請求書発行 (3)申告書類の自動下書き。
  （初期は撮影→仕訳だけで検証可能。請求書機能は後回しにできる）。
- **手順⑤チャネル/収益/コスト**: チャネル=フリーランス向けコミュニティ・紹介。収益=月額サブスク。
  コスト=開発・OCR等の外部サービス利用料。
- **手順⑥主要指標**: 「継続利用率（登録後も毎月レシートを記録し続ける人の割合）」を単一指標に。
- **手順⑦優位性**: 現時点では明確な優位性は無いと正直に空欄。今後「初心者向けの分かりやすさ」と
  コミュニティ内の信頼を築く対象として置く。
- **手順⑧検証順**: 最重要かつ確証が薄いのは課題(1)「記録が続かない」の深刻さ。ここが弱いと全体が崩れる。
- **出力(検証計画)**: 最優先=「記録が続かない課題は本当に痛いか」→ 対象層10人に既存の代替手段と不満を
  ヒアリング。判定=「大半が現状に強い不満を語り、代替に手間・お金を払っている」ならOK。
- **未確認の前提**: 「初心者は撮るだけなら続く」は未検証の仮説——プロトタイプでの継続を実測するまで確定しない。

## 相性（組み合わせると効く）

- `business-model-canvas`: 対比・上位。確立事業の全体設計や記述にはBMCへ。検証段階を過ぎたらこちらに移す。
- `value-proposition-canvas`: 課題(Problem)と顧客(Customer Segments)、UVPの噛み合わせ（Fit）を深掘りする直接の続き。
- `jtbd`: 課題ブロックを「顧客が片付けたい用事」で捉え直し、機能起点の思い込みを揺さぶる（発想レンズ）。
- `persona`: 顧客セグメント／アーリーアダプターを具体的な人物像に落とし込み、検証対象を明確にする。
- `lean-startup-mvp`: キャンバスの「検証計画」をMVP・実験に渡し、仮説を実地で回す次工程。
- 揺さぶり枠として `premortem`（「この事業が1年後に失敗したとして、どの前提が外れたか」を先回り）や
  `devils-advocate`（UVPや優位性の過信を反対役で突く）を添えると、検証すべきリスクの見落としが減る。
